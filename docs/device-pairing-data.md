# DP-03. Адаптеры данных и журнал применения

26 октября 2026 года. Реализован ограниченный backend обмена preferences/views/playback, журнал main/renderer и подтверждённая сверка снимком. Обычный запуск Havvn пока не подключает этот backend, IPC endpoint или сетевой listener. Пользовательский экран и подключение к событиям работающего приложения относятся к DP-04; FUN-06 остаётся открытым.

## Разрешённые данные

`shared/device-data.ts` проверяет каждую операцию до записи в журнал. Версия, поля, типы, размер и идентификаторы строгие. Произвольный localStorage key, токен, путь запуска, настройка сети или команды не принимаются.

Предпочтения: только `language`, `uiScale`, `density`, `reduceMotion`, `speedUnits`, `audioLanguage`, `subtitleLanguage`, `subtitleMode`. Значения интерфейса проходят существующий `validateInterfacePreferences`; языки и режим субтитров проверяются до применения нормализатора. Ошибочное сетевое значение не превращается в значение по умолчанию. Удаление интерфейсного значения удаляет ключ, удаление выбранного поля плеера возвращает его штатное значение по умолчанию; остальные поля плеера сохраняются.

Виды используют `syncViewId`, который явно связывается с локальным ID через `havvn.devices.data.v1`. Передаются имя, условия, сортировка, плотность и закрепление. Фильтр локального пути **не передаётся**: `exportDeviceView` возвращает `path-filter`, сохраняя исходный локальный вид. Входящий непустой path отклоняется. Категория требует явно заданного отображения в существующий локальный ID; отсутствие соответствия оставляет запись ожидающей. Имя категории не используется для угадывания.

Порядок — отдельная причинная запись `order`. Сначала должны существовать соответствующие локальные виды; переставляются только их позиции, остальные локальные строки сохраняются. Текущий активный вид не импортируется. Удаление активного локального вида переводит локальный выбор в общий список, поскольку ссылка на удалённый вид недопустима. Удаление синхронизированной записи остаётся tombstone в main.

Позиция просмотра содержит только infoHash, относительный путь, точный размер, позицию, длительность и отметку просмотра. `media.<sha256>` считается по каноническим infoHash/path/size и проверяется в main. Абсолютные пути, traversal, fallback по downloadId/имени, неверная длительность и выход за неё отклоняются. Локальные downloadId/title/fileIndex берутся из доверенного каталога получателя, а не от партнёра. Отсутствующий, неоднозначный или открытый файл остаётся ожидающим. Адаптер не скачивает файл и не вызывает seek/play; явный повторный просмотр с нуля применяется как причинное изменение, без выбора наибольшей позиции.

## Состояние и причинность

`electron/devices/replica-state.ts` реализует двухавторский multi-value register для каждого scope/recordId. Это рабочий backend, отдельный от старой исследовательской модели.

- Новая локальная операция, её глобальный счётчик области, причинный регистр и outbox публикуются одной OS-защищённой записью vault.
- Офлайн-правки двух устройств сохраняются двумя heads. Ни часы ОС, ни величина позиции просмотра не выбирают победителя.
- Локальная публикация проверяет, что выбранное значение действительно находится в renderer, и связывает новую операцию с полным известным контекстом записи. Так явное решение пользователя причинно замещает обе ветки.
- Входящая граница подтверждения непрерывная. Перестановка может применить независимую запись, но ACK не перескакивает дырку или неприменённую запись.
- В окне максимум 64 незакрытых номера. Повтор ID с другим содержимым останавливается; старый ID под закрытой границей не применяется повторно.
- Партнёр не может выдумать локальный dot, выпущенный для другой записи. Snapshot также не может объявить неизвестную локальную операцию своей известной веткой.

Внутри прежнего защищённого `device-state.json` добавлено `replica`: регистры, входящие окна, локальные границы, один apply journal и состояние resync. Отдельной незашифрованной БД нет. Старый DP-01/DP-02 контейнер без `replica` читается как пустой журнал без перезаписи на open. Старые произвольные исследовательские outbox-сообщения не превращаются автоматически в переносимые данные: публикация и snapshot требуют последовательной истории нового адаптера; при смешанной истории нужен новый подтверждённый grant.

## Журнал main/renderer

`DeviceReplicator` координирует vault и доверенный `DeviceDataTarget`. Для настоящего renderer есть явные фабрики `attachDeviceRendererTarget` в main и `attachDeviceDataClient` в preload. Они не вызываются существующим main/preload при обычном запуске.

1. Принятые данные и состояние дедупликации сохраняются в main. Это ещё не ACK применения.
2. Renderer строит ограниченный before/after patch для конкретных разрешённых ключей. Main связывает его с точным набором heads; устаревший план не получает права на запись.
3. Main устойчиво сохраняет prepared journal до отправки команды применения.
4. Preload сверяет весь patch с текущим before/after, затем перед записью каждого ключа синхронно запрашивает авторизацию. Main проверяет конкретный WebContents/main frame, случайный request ID, вид команды, хеш сохранённого journal, grant и область. Для применения повторно проверяются актуальные категория, каталог файла и признак открытого плеера.
5. Renderer читает записанное обратно. Только затем main фиксирует stamp, завершает journal и продвигает непрерывный ACK. Отправитель удаляет outbox после получения этого аутентифицированного ACK.

Синхронная IPC-авторизация отвечает ровно один раз. Это отдельно проверено после ошибки, обнаруженной настоящим Electron: предварительная отправка false не должна опережать разрешающий ответ. Результат другого окна/дочернего frame, неизвестный lease, таймаут и закрытый endpoint не подтверждают запись.

После сбоя незавершённый patch повторяется только для ключей, оставшихся в известных состояниях before/after. Уже сохранённое значение не записывается повторно, частичный двухключевой commit дописывает недостающую часть. Неожиданная локальная правка не перезаписывается. `preview` показывает актуальное состояние; только подтверждение того же heads и точного beforeStamp позволяет перепланировать этот journal и повторить применение.

## Renderer-кэш и значение ACK

ACK означает устойчивый коммит канонических данных/причинных границ в защищённом main **после** чтения renderer-результата. Он не является доказательством fsync базы Chromium. Даже вызов [Electron `flushStorageData`](https://github.com/electron/electron/blob/v44.4.2/docs/api/session.md#sesflushstoragedata) не используется как отдельное подтверждение завершения записи: API не возвращает promise такого подтверждения.

Нативный тест прерывает процесс после renderer readback, но до main finish. При новом запуске target может оказаться в before или after; prepared main journal восстанавливает оба случая и только затем разрешает ACK. Исходная слишком строгая проверка сохранения только after не прошла под нагрузкой; её лог сохранён в `artifacts/dp03-native-cache-loss.log`.

После уже завершённого ACK каноническое значение всё равно остаётся в main. `recover()` проверяет материализацию регистров в renderer. Если кэш отличается, данные не забываются и автоматического выбора между потерянным кэшем и возможной несохранённой локальной правкой нет: появляется `local-change`, доступен точный preview и явное восстановление. Этот случай отдельно проверен. DP-04 должен запускать восстановление до показа результата синхронизации и явно показывать ожидающее локальное применение. Пока UI этого не делает, пользовательская функция выключена.

## Отзыв и изменение областей

Отзыв сразу приостанавливает авторизацию и закрывает TLS-сессии. Затем vault ждёт начатую запись target, проверенно откатывает незавершённый patch и только после этого публикует tombstone. Успешный отзыв не оставляет разрешённую запись, которая сможет завершиться позже. Rollback lease разрешает только точный сохранённый patch; произвольное новое сетевое значение через него не применяется.

Ошибка отката/хранения оставляет paused-error; успех не сообщается, журнал сохраняется. Без подключённого endpoint отката pending journal нельзя просто выбросить. При сужении областей используется тот же барьер; все соединения временно закрываются, удалённая область перестаёт применяться и отправляться. Расширение требует нового grant. Параллельный отзыв не отменяется завершением более раннего сужения.

Уже завершённые применения и ранее отправленные сетевые байты отзыв назад не стирает. После нового grant старые сообщения не подходят.

## Подтверждённый snapshot/resync и бюджеты

`DeviceSession` переносит отдельный `snapshot` по тому же закреплённому mTLS-каналу. Снимок содержит область, watermark и полный передаваемый набор регистров с обеими ветками, контекстами и tombstones. Локальные patch/stamp и renderer metadata в сеть не уходят. Слияние сохраняет одновременную локальную ветку и уже известные удаления.

Первый импорт требует callback с явным согласием на digest/область/число записей. Повтор того же уже подтверждённого незавершённого снимка не требует нового согласия. Его watermark сохраняется, но не становится ACK до применения всех результирующих записей; конфликт, категория или локальная правка продолжают блокировать продвижение. Проверен resync заполненной outbox из 1000 операций с последующей публикацией сохранённого локального изменения. До ACK отправитель ничего не выбрасывает.

Бюджеты прототипа: операция до 4 КиБ, до 256 регистров вместе с tombstones, окно 64, replica до 3 МиБ, prepared patch до 1 МиБ/3 ключей, до четырёх IPC-запросов, таймаут endpoint 10 секунд. Сохраняются прежние верхние границы outbox 1000/8 МиБ и общего plaintext envelope 9 МиБ; они не обещают одновременное достижение всех максимумов.

Snapshot пока помещается в один кадр до 64 КиБ. Более крупный снимок отклоняется с size, без усечения, продвижения ACK или потери tombstone; multipart/resync больших каталогов не реализован. Переполнение не запрещает обычное локальное редактирование: публикация сообщает ошибку и оставляет renderer-значение на месте. До выпуска UI обязан показывать такое состояние и не сообщать «синхронизировано».

## Проверки и оставшиеся границы

```powershell
npm run test:device-data
npm run test:device-data-native
npm run typecheck
npm run build
```

Целевой набор: **123 теста в 10 файлах**, включая 42 новых проверки схем, причинности, IPC, журнала и реального TLS-переноса snapshot. Нативный стенд использует настоящий Electron, safeStorage/DPAPI, два persistent renderer partition и три запуска main. Родитель завершает только собственный тестовый процесс через SIGKILL после prepared main journal и renderer readback. Приёмка также проверяет частичную запись вида, отсутствующий/открытый файл, локальные метаданные истории, повторный просмотр с нуля и отзыв при незавершённой записи. Каталог файлов и согласия стенда синтетические; это не пользовательский UI, настоящее воспроизведение или LAN.

Итог: **4290 Vitest-тестов в 329 файлах**, **30 Node-тестов**, **28 нативных проверок в трёх процессах main**. В финальном аварийном прогоне renderer действительно вернулся к before, а защищённый prepared journal восстановил значение до ACK. Проверка типов трёх сборок, линтер изменённого кода и полная сборка прошли; сохранились три прежних предупреждения webpack о размере/структуре bundle.

Числа полного прогона, точные нативные проверки, версии и хеши: [приёмка DP-03](device-pairing-data-acceptance.json). Старые свидетельства DP-00…DP-02 и исторический график не переписаны.

Отдельная граница: авария самой первой инициализации профиля/OS encryption не входит в успешный crash-сценарий. В первоначальном эксперименте следующий процесс получил locked; отказ был закрытым, без автоматической замены идентичности. Стенд сначала выполняет отдельную штатную инициализацию, затем проверяет сбой обмена. Первый запуск, восстановление OS keyring/профиля и понятный пользовательский маршрут остаются обязательными перед включением DP-04. Power-cut, установщик и Linux в этом прогоне не проверялись.

26 октября пользователь сообщил о втором устройстве — Linux-ноутбуке. Подключение ещё не настроено: фактические прогоны по-прежнему выполнены на одном Windows-ПК. Для будущей приёмки нужны доступ к ноутбуку, графическая сессия/keyring для нативного Electron и отдельно доступные сетевые маршруты. SSH может управлять стендом; сам по себе он не доказывает успешную проверку LAN/NAT. Второй ПК больше не отсутствует как оборудование, но FUN-01/DP-05 пока не закрыты.
