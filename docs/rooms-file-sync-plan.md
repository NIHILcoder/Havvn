## 1. Продуктовое решение

Развивать функцию тремя самостоятельными выпусками:

1. **Обновляемая папка:** один назначенный участник публикует изменения, остальные получают их автоматически. Есть история, восстановление, пауза и понятное состояние доставки.
2. **Двусторонняя синхронизация:** несколько участников изменяют локальные файлы; независимые правки одного файла сохраняются как конфликт, который можно разрешить.
3. **Совместные заметки:** встроенный текстовый редактор с одновременной работой, курсорами, офлайном и экспортом. Форматированный редактор и Office-совместимость оцениваются отдельно.

Каждый выпуск должен быть полезен без следующих. Первый закрывает конфиги, общие материалы и передачу изменений с рабочего ноутбука на домашний ПК. Второй закрывает редактирование с обоих устройств. Третий закрывает общие заметки и списки задач внутри комнаты.

Принять для первого выпуска: desktop Windows; Linux проходит отдельную проверку перед объявлением поддержки. Браузерные гости и старые клиенты не участвуют в файловой синхронизации. Произвольный файл поддерживается как последовательность байтов: `.docx`, `.xlsx`, `.sln`, `.csproj` не требуют отдельных парсеров для передачи после сохранения.

Совместное редактирование Word/Excel в реальном времени в эти обещания не входит. Для проекта с `.sln` синхронизируется выбранное дерево исходников, а не только файл решения.

- `electron/sharing/room-file-storage.ts`: отдельные управляемые копии, проверка торрент-метаданных и содержимого, работа с зашифрованными файлами.
- `shared/room-manifest-sync.ts`: постраничный обмен и ограничения — 5000 файлов и 16 МиБ метаданных обычного манифеста.
- `shared/room-capabilities.ts`, `shared/room-protocol.ts`, `shared/room-message-auth.ts`: согласование возможностей, валидация и проверка подписей.
- `electron/sharing/room-manager.ts`, `electron/db/store.ts`, `shared/room-state-ipc.ts`: основной процесс, локальное хранение и передача изменений состояния в UI.
- `shared/room-folders.ts`: папки — группировка обычного манифеста. Они не представляют произвольное дерево локальной файловой системы.

В просмотренном файловом пути есть сканирование при восстановлении комнаты, но нет полноценного постоянного наблюдения за изменениями исходников. Существующий `watchFile` в менеджере относится к воспроизведению медиа.

## 3. Архитектурные решения

### 3.1. Отделить документ от его содержимого

Добавить новый домен синхронизации рядом с обычными публикациями. Не менять смысл существующего `RoomFile.fileId`.

- `SyncRoot`: общая папка с постоянным `rootId`, названием и политикой публикации.
- `SyncEntry`: постоянный `entryId` файла внутри корня; текущие версии и относительный путь.
- `SyncRevision`: неизменяемое описание изменения: `revisionId`, `rootId`, `entryId`, `parents[]`, операция, относительный путь, ссылка на содержимое, автор, версия политики и подпись.
- `BlobRef`: описание конкретного передаваемого содержимого — `infoHash`, размер, торрент-метаданные и параметры существующего E2E-шифрования.
- `LocalBinding`: локальный путь корня, режим получения, применённые версии, отпечатки файлов, ожидающие операции и локальные исключения. Не передаётся участникам комнаты.

`revisionId` вычислять по каноническому описанию ревизии без подписи, с разделением доменов протокола. Подпись связывает ревизию с комнатой и корнем; `parents` отсортированы и проверяются. Время используется для отображения, а не выбора победителя.

В первом выпуске ревизии образуют цепочку, но поле `parents[]` сразу допускает последующее объединение ветвей. Перенос одного содержимого в два пути создаёт два объекта, а не склеивает документы по хешу. В E2E-комнате транспортный хеш относится к шифротексту; повторное шифрование тех же байтов может дать другой хеш. Принадлежность к документу от этого не меняется.

### 3.2. Переиспользовать передачу без засорения обычного манифеста

Выделить небольшой адаптер `RoomBlobTransport` к текущему движку: подготовить неизменяемую копию, раздавать, получить, проверить, удержать ссылку, освободить ссылку.

Обычные публикации и ревизии используют общий механизм передачи, но отдельные индексы. Каждое сохранение не добавляет карточку в `room.files` и не расходует лимит его 5000 записей. Учёт доступности и выдача содержимого проверяют соответствующий индекс, комнату и подписанную ревизию.

Не копировать весь `room-engine.ts` и не устраивать общий рефакторинг движка. Сначала выделить минимальный контекст передачи вместо жёсткой проверки только через `room.files`; сохранить тесты обычных публикаций. До начала основной реализации подтвердить это небольшим техническим прототипом.

Содержимое новой версии в первом выпуске передаётся целиком существующим транспортом. Межверсионные дельты, собственный блочный протокол и дедупликацию шифротекста отложить до измерений. Изменившийся хеш торрента не означает автоматическое переиспользование блоков старой версии.

### 3.3. Общая политика и локальная запись — разные настройки

Владелец комнаты задаёт подписанную политику корня: назначенный издатель, позднее список редакторов, версия политики и разрешение публикации удалений. Смена политики образует проверяемую цепочку; старый снимок не откатывает уже принятую политику.

Каждый участник сам выбирает локальную папку и включает применение обновлений. Общая настройка комнаты не предоставляет право записи в произвольный путь на чужом компьютере. Издатель работает с отдельной идентичностью своего устройства; копировать одну identity между одновременно работающими ПК не требуется.

Обычная автозагрузка продолжает действовать для обычных файлов. Для синхронизации есть отдельные переключатели «получать версии» и «применять в локальную папку».

Единица первой реализации — `SyncRoot`, связанный с разделом интерфейса комнаты. Отдельный файл можно представить корнем с одним явно выбранным объектом. Массовое включение на всю комнату добавить позже как действие настройки корней. Для уже существующих публикаций требуется явный импорт выбранных файлов; прежние оригиналы не начинают изменяться автоматически.

## 4. Первый выпуск: поведение пользователя

1. В меню файлов комнаты — «Создать обновляемую папку».
2. Владелец выбирает издателя. По умолчанию это создатель корня.
3. Издатель выбирает локальную папку, видит список включаемых файлов и исключения.
4. Получатель выбирает папку назначения. По умолчанию предлагается новая пустая папка в пользовательских данных, вне служебного каталога комнаты и кэша; существующее дерево сначала сравнивается.
5. После сохранения издателем остальные участники получают проверенную версию и применяют её, если локальный файл не имеет собственных изменений.
6. В карточке доступны: пауза, обновить сейчас, открыть папку, история, восстановить версию, отвязать папку.

Локальное изменение на стороне получателя сохраняется. Файл получает состояние «Локальные изменения»; автоматическая замена для него приостанавливается. Действия: сохранить свою копию и принять общую либо оставить файл на паузе. В первом выпуске эта правка не становится общей автоматически.

Восстановление старой версии издателем создаёт новую ревизию поверх текущей. История и защита от повторной доставки не откатываются.

Состояния: «Актуально», «Подготовка», «Ожидает источник», «Получение», «Проверка», «Применение», «Локальные изменения», «Файл занят», «Недостаточно места», «Приостановлено», «Нужна новая версия Havvn».

Указывать отдельно: сохранено на этом устройстве; копия подтверждена доступным участником; состояние остальных неизвестно. Нельзя обещать доставку на выключенный ПК. Источником может быть любой участник с сохранённой копией, а не только издатель.

## 5. Путь локального изменения

1. Наблюдатель сообщает о возможном изменении; изменение ставится в очередь одного корня.
2. Объединить серию событий, дождаться периода покоя и стабильных `stat`. Начальный ориентир — 1–2 секунды, затем настроить по проверкам Office/IDE.
3. Скопировать файл в неизменяемую служебную копию; потоково посчитать хеш. Проверить, что источник не изменился во время подготовки; иначе повторить. Одинаковое содержимое не порождает новую ревизию.
4. Для E2E-комнаты использовать существующий жизненный цикл ключей, шифрование и проверку содержимого. Старые ключи нужны для доступных старых версий. Открытые служебные копии имеют ограниченный срок жизни и учитываются очисткой.
5. Подготовить и проверить раздаваемую копию. Сохранить ревизию и исходящую очередь на диск до сетевого объявления.
6. Объявить метаданные, затем передавать байты по запросу. После перезапуска продолжить объявление без создания дубликатов.

Использовать Chokidar как адаптер наблюдения, зафиксировав подходящую для встроенного Node/Electron версию после проверки. Не считать событие watcher доказательством готовой записи.

Периодический ограниченный обход обязателен: при старте, возобновлении системы, восстановлении наблюдателя и по таймеру. Начальный ориентир — раз в 10 минут с разнесением по времени. Проверяются прежде всего метаданные; полное хеширование выполняется для кандидатов и по команде глубокой проверки. Изменения с сохранёнными размером и временем могут потребовать глубокой проверки — не обещать обнаружение любых изменений одним `mtime`.

По умолчанию исключить служебные каталоги Havvn, `.git`, `.vs`, `node_modules`, `bin`, `obj`, Office lock-файлы и временные файлы. Предоставить локальные и общие правила исключений с предварительным просмотром. Секреты вроде `.env` и приватных ключей исключить в стартовом профиле проекта, с явной возможностью включения нужных файлов.

Не следовать симлинкам и junctions в первом выпуске. Запретить пересекающиеся локальные корни, привязку к служебному кэшу и передачу файлов восстановления. Для физического дерева хранить относительный путь независимо от ограниченной иерархии `RoomFolder`.

## 6. Получение, применение и восстановление после сбоя

1. Проверить рамку, подпись ревизии, права автора, политику, родителей и бюджеты до скачивания.
2. Записать ожидающую ревизию; при неизвестном родителе запросить недостающую метаинформацию. Не подменять отсутствующую историю сравнением дат.
3. Скачать содержимое в управляемое staging-хранилище, проверить торрент и результат расшифровки. Текущий пользовательский файл до этого остаётся доступным.
4. Получить очередь/блокировку объекта; сравнить текущий файл с последней применённой версией. Несовпадение означает локальную правку, а не разрешение на перезапись.
5. Подготовить замену на том же томе, сохранить предыдущие байты и журнал применения. Снова проверить путь и локальное состояние непосредственно перед заменой.
6. Заменить файл поддерживаемой операцией ОС. Отдельно проверить поведение Windows при открытом файле и сохранении внешней программой. При блокировке ждать и повторять с ограничением частоты.
7. Зафиксировать применённую ревизию. Подавить обратную публикацию по ожидаемой версии/хешу и происхождению операции; временного флага `ignoreWatcher` недостаточно.
8. После запуска восстановить незавершённую операцию по журналу и фактическим файлам. Состояние «Актуально» показывать только после завершения фиксации.

Атомарность одиночного переименования не равна транзакции с Word/IDE или всем деревом проекта. Нельзя обещать отсутствие гонок с любой внешней программой. Прототип должен подтвердить допустимый способ замены на Windows; при невозможности безопасного применения оставлять обновление ожидающим. Сохранённая предыдущая копия и журнал не удаляются до завершения операции.

Для первого выпуска применяется каждый файл отдельно. Можно получить промежуточное сочетание версий проекта; это явно указать. Согласованный снимок дерева, отложенное применение набора и интеграцию с остановкой игрового сервера добавить отдельным улучшением при подтверждённой потребности.

Удаление исходного файла сначала выдерживает задержку, чтобы не принять сохранение через временное переименование за удаление. Удаления публикуются только при включённой политике; получатель переносит управляемую копию в историю/корзину. Пропажа диска или недоступность корня никогда не трактуется как удаление всего дерева.

## 7. Сетевой протокол и совместимость

Добавить capability `file-sync-v1`, позднее отдельные `file-sync-v2` и `documents-v1`. Не использовать существующий `sync-v2`: он относится к совместному воспроизведению.

Отдельные типы сообщений для политики, страницы индекса, запроса недостающих ревизий, объявления ревизии и подтверждения сохранённой копии. Названия и канонический формат зафиксировать в ADR до реализации. Индекс содержит текущие головы и достаточно сведений для проверки; история запрашивается страницами, а не целиком в каждом HELLO.

Опора на существующие соединения комнаты, подписи, проверку идентичностей и шифрование транспортных сообщений. Обновить общий валидатор, проверку доказательств, списки ретрансляции и ограничения нагрузки. Метаданные и авторизованные запросы проходят через совместимые узлы; поведение смешанной сети проверить отдельно. Старые клиенты не обязаны ретранслировать неизвестные сообщения — им нельзя поручать связность новой функции.

Исходящие метаданные и подтверждённая голова сохраняются до отправки. Дубликаты, перестановка страниц и повтор после reconnect идемпотентны. Сводка/запрос недостающего состояния восстанавливают потерянные объявления.

При смене издателя или отзыве прав принять зафиксированный новым владельцем политики базовый набор голов. Поздние записи прежней политики не продвигают активное состояние автоматически; сохранять их для разбора. Уже переданные байты нельзя отозвать у бывшего участника.

Начальные предлагаемые бюджеты: 8 корней на комнату, 2000 текущих файлов суммарно, 256 МиБ на автоматически обновляемый файл, до 64 записей и 96 КиБ на страницу, ограниченная очередь хеширования и две передачи на комнату. Это проектные настройки для первого выпуска, а не результаты замеров. При достижении лимита приостанавливать новые операции с понятной причиной. Скорректировать бюджеты по прототипу и использовать имеющиеся общие лимиты трафика и приоритет голоса.

## 8. Хранение, история и очистка

Добавить отдельный `electron/db/room-sync-store.ts`: версия схемы, политика, текущие головы, компактные ревизии, исходящие записи и локальные привязки. Использовать существующий подход атомарной записи ограниченных JSON-снимков, с разделением по корням и пакетированием изменений. Не переписывать весь `rooms.json` при каждом сохранении. Бинарные данные хранятся отдельными файлами.

Не вводить собственную универсальную БД или SQLite без измеренной необходимости. Небольшой журнал применения нужен для согласования замены пользовательского файла и записи локального состояния; это не новый общий движок хранения.

Предлагаемые значения истории: до 20 предыдущих версий файла, срок 30 дней, общий локальный бюджет истории комнаты 1 ГиБ. Эти ограничения относятся к архивным байтам; текущие рабочие копии и незавершённые операции учитываются отдельно. При невозможности сохранить обязательную предыдущую копию обновление ждёт освобождения места.

Ревизии могут разделять одну копию содержимого. Считать ссылки от текущих голов, конфликтов, истории, активных загрузок и операций восстановления. Не удалять занятый торрент и последний нужный локальный источник без обработки его ссылок. История байтов может быть локально очищена; UI отличает запись истории от реально доступного содержимого.

Причинные метаданные, границы принятой политики и сведения об удалениях не очищаются только потому, что истёк срок хранения байтов. В первом выпуске допустимо хранить ограниченный журнал ревизий с явной остановкой публикации при заполнении; порог и размер проверить нагрузкой. Безопасные подписанные checkpoints и компактация — обязательный отдельный шаг перед длительной эксплуатацией двусторонней синхронизации. Вернувшийся давно офлайн участник после компактации проходит полную сверку и сохраняет свои независимые изменения.

Восстановление старой версии из истории возможно только при наличии её байтов локально или у доступного участника. Синхронизация и распределённые копии не гарантируют архив после потери всех источников. Показывать подтверждения хранения как последнее известное состояние, не как вечную гарантию.

В экспорт восстановления комнаты включать метаданные синхронизации в новой версии формата, но не локальные пути и разрешения записи. После импорта — новая привязка и применение выключено. Выход из комнаты останавливает наблюдение и задачи; пользовательская папка и оригиналы остаются. Отвязка прекращает синхронизацию без сетевого удаления файлов.

## 9. Второй выпуск: несколько авторов

После стабилизации первого выпуска включить редакторов по подписанной политике корня. Использовать граф ревизий с родителями:

- потомок текущей головы применяется последовательно;
- независимые потомки общего предка дают несколько голов;
- при разных байтах появляется конфликт, обе версии удерживаются;
- одинаковый результат разных ветвей можно объединить новой явной ревизией;
- разрешение конфликта создаёт ревизию со всеми разрешаемыми головами в `parents`;
- удаление против независимого редактирования — конфликт, а не молчаливое уничтожение;
- неизвестные или уже скомпактированные родители запускают сверку, а не выбор по времени.

Пользователь выбирает «Принять версию», «Сохранить обе» или для текста «Сравнить и объединить». Для `.docx`/`.xlsx` автоматического слияния нет. Не вводить распределённую блокировку как условие корректности: офлайн-изменения всё равно требуют конфликтов. Статус «Сейчас редактирует» можно добавить как подсказку.

Файловые переименования первого выпуска могут быть удалением и созданием. Во втором добавить явный перенос стабильного `entryId`; эвристическое обнаружение переименования не должно склеивать одинаковые файлы. Коллизии путей, различия регистра и одновременные переносы обрабатываются как отдельные конфликты. Проверку Windows-имён, зарезервированных имён, длины, `..`, ADS, симлинков, junctions и жёстких ссылок выполнять на границе работы с диском.

## 10. Третий выпуск: совместные заметки

Начать с UTF-8 текста и Markdown. Выбрать Yjs + CodeMirror 6 после маленького прототипа. У Yjs есть готовые привязки редакторов и обмен состоянием; собственный алгоритм CRDT не нужен. Написать провайдер поверх соединений комнаты, без отдельного публичного сервиса обнаружения.

Документ имеет собственный `documentId`. Авторитетное состояние — сохранённый CRDT и журнал принятых обновлений; экспорт `.txt`/`.md` — материализованный снимок. Поддержать автоматическое сохранение этого снимка в выбранный локальный файл после короткого периода покоя; история снимков создаётся по интервалу или явному сохранению, а не на каждую клавишу. Не синхронизировать одновременно экспортированный файл и CRDT как два равноправных источника. Импорт внешней правки — отдельное действие с новой транзакцией либо новым документом; внешние изменения экспортного файла не затираются молча.

Изменения документа идут небольшими обновлениями, а не торрентом на каждую клавишу. Провайдер обеспечивает сверку state vector, повторную доставку, локальное сохранение до статуса «сохранено», дедупликацию и проверку прав. Курсоры/выделения — отдельное временное awareness-состояние; оно не записывается в историю документа. Ограничить частоту, размер пакетов, размер документа и потребление памяти при применении обновлений.

Подпись конверта связывает обновление с автором, документом, комнатой и политикой; CRDT сам по себе не проверяет доступ. Объединённые снимки требуют понятной модели доверия: сохранять проверяемое происхождение обновлений либо использовать уполномоченного создателя checkpoint, не принимать произвольный объединённый снимок от читателя. Ротация ключей, отзыв прав, восстановление после офлайна и защита от старой политики проверяются отдельно.

После подтверждения спроса добавить форматированные заметки через ProseMirror/Tiptap и оценить импорт/экспорт DOCX. Сохранение оформления, таблиц, комментариев и совместное редактирование Office требуют отдельного исследования; не приравнивать наличие CRDT к полной совместимости Word/Excel.

## 11. Порядок работ и критерии перехода

### Шаг 0. ADR и технический прототип

Согласовать модель ревизии, политику первого выпуска, границы полномочий и поведение существующих файлов. Проверить адаптер передачи вне обычного манифеста, замену открытых файлов на Windows, сохранения Office через rename, E2E и смешанную сеть клиентов. Измерить обработку 2000 небольших файлов и файла на границе выбранного лимита. Зафиксировать исходные CPU/RAM/время восстановления и влияние на голос.

Готово: есть работающий изолированный прототип и ответы по трём рискам — передача, безопасное применение, восстановление. Численные цели производительности устанавливаются по измерениям до расширения реализации.

### Шаг 1. Модель и локальное хранилище

Чистые функции ревизий, валидация, канонизация подписей, политика, схема хранения, исходящая очередь и локальные привязки. Пустая миграция существующего профиля, запрет автоактивации.

Готово: дубликаты и перестановка ревизий дают одно состояние; неавторизованный автор и старая политика не меняют головы; перезапуск сохраняет ожидающие операции.

### Шаг 2. Наблюдение и неизменяемые версии

Наблюдатель, ограниченный обход, исключения, очередь подготовки, стабильные копии, E2E, повтор после сбоя.

Готово: одно обычное сохранение даёт одну опубликованную версию; временные файлы и применение своей загрузки не вызывают циклов; меняющийся файл не публикуется как готовый.

### Шаг 3. Передача и догоняющая синхронизация

Адаптер blob-передачи, capability, валидаторы, подписи, индекс страницами, запрос недостающих ревизий, доступность копий и восстановление после reconnect.

Готово: два desktop-клиента получают одинаковые метаданные и байты после потерь/повторов; старый клиент работает с обычными файлами; E2E не раздаёт исходник открытым текстом.

### Шаг 4. Применение, история и жизненный цикл

Staging, резервная версия, журнал применения, защита локальных правок, удаление в корзину, откат новой ревизией, квоты, остановка при leave/kick/suspend и очистка.

Готово: сбой между каждой стадией восстанавливается; занятый файл и нехватка места оставляют рабочую копию доступной; очистка не удаляет используемые версии и оригиналы.

### Шаг 5. Интерфейс и первый выпуск

Мастер привязки, предварительное сравнение, карточки состояния, история, настройки исключений, отображение доступности источников и отдельные настройки автоприменения. Включить i18n и доступность; сохранение существующих размеров/тем и рабочих пространств комнаты.

Готово: пользователь без чтения документации создаёт корень, подключает второй ПК, получает обновление, восстанавливает версию и корректно отвязывает папку. Проверена упакованная Windows-сборка на двух отдельных профилях/ПК.

### Шаг 6. Двусторонняя синхронизация

Несколько авторов, несколько голов, разрешение конфликтов, явные переименования, безопасные checkpoints и возврат давно офлайн устройств. Выпускать только после полного набора проверок конфликтов и компактации.

### Шаг 7. Совместные заметки

Прототип редактора и провайдера, устойчивое хранение CRDT, проверяемые сетевые обновления, курсоры, офлайн, экспорт и история снимков. Отдельный выпуск с отдельным бюджетом памяти/сети.

Шаги 1–5 разбивать на небольшие PR по этим границам. Пользовательский первый выпуск готов только после шага 5; промежуточные PR скрыты за локальным выключенным флагом. Для шагов 6–7 понадобятся собственные PR. Срок в днях назначать после шага 0 и выбора исполнителей, без искусственного обещания «сделать синхронизацию за пару дней».

Предлагаемые новые модули:

Проверки IPC ограничивают вызовы локальной комнатой и выбранной привязкой; удалённые сообщения не содержат произвольных локальных путей назначения.

Работу с пользовательским диском и наблюдателями держать в основном процессе, сетевой обмен — в текущем движке скрытого окна. Тяжёлое хеширование/подготовка выполняются потоково с ограниченной конкуренцией; вынос CPU-нагрузки в worker решается по измерениям. Все задания имеют lifecycle token: результат старой сессии не применяется после переподключения, смены политики или выхода.

1. **Обычный путь:** конфиг, Markdown, DOCX, XLSX и дерево небольшого C#-проекта; сохранение в штатных программах; первый импорт в пустой и непустой каталог.
2. **Запись:** серия автосохранений, длинная запись большого файла, rename-based save, нулевой файл, переименование/удаление, остановка приложения в процессе подготовки.
3. **Сеть:** офлайн издатель/получатель, третий участник как источник копии, разрыв во время загрузки, потеря объявления, дубликаты и перестановка страниц, смешанные версии клиентов.
4. **Локальные данные:** изменение получателем, файл занят, ENOSPC, диск отключён, каталог исчез, совпадение имён с разным регистром, длинные/неподдерживаемые имена, симлинки/junctions/hardlinks.
5. **Восстановление:** принудительная остановка на каждой стадии применения; перезапуск без создания лишней версии; очистка во время загрузки и восстановления; исчерпание квоты истории.
6. **Права и E2E:** поддельная ревизия, подмена ссылки на байты, повтор из другой комнаты, старая политика, смена издателя/владельца, kick и ротация ключей; старые версии с прежними ключами.
7. **Производительность:** выбранные лимиты дерева/размера, пакетная замена сотен файлов, нагрузка на IPC и хранилище; активный голос и обычные загрузки во время синхронизации.
8. **Второй выпуск:** офлайн-правки двух/трёх авторов, edit/edit, edit/delete, move/edit, совпадение содержимого при разных предках, разрешение конфликтов и возврат после checkpoint.
9. **Заметки:** одновременная печать и удаление, disconnect/rejoin, перезапуск обоих клиентов, частичная доставка, неверные права/эпоха, большой вредоносный пакет, курсоры, undo и корректный экспорт.

Чистые правила проверять Vitest; диск и аварийное восстановление — интеграционными тестами на временных каталогах; сеть и UI — существующим стилем Electron smoke/acceptance. Реальные блокировки Office и работа между ПК требуют ручной приёмки. Перед соответствующим выпуском выполнить `npm test`, `npm run typecheck`, `npm run build` и новые целевые сценарии; наборы следующих выпусков не блокируют первый, если их функции выключены.

- [Chokidar: наблюдение, atomic и awaitWriteFinish](https://github.com/paulmillr/chokidar). Адаптер наблюдения не заменяет проверку снимка.
- [Yjs: модель и существующие интеграции редакторов](https://docs.yjs.dev/).
- [Yjs: обновления, state vector и провайдер](https://docs.yjs.dev/api/document-updates). Механизм согласования текста не предоставляет авторизацию и надёжное хранение автоматически.
