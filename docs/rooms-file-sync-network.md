# Синхронизация файлов: подключение к настоящим комнатам

Текущая сводка локальных, пакетных и внешних проверок: [FUN-01](rooms-release-acceptance.md). Ниже сохранено описание сетевого этапа 17 октября.

17 октября 2026 года. Продолжение [плана](rooms-file-sync-plan.md), [файлового прототипа](rooms-file-sync-spike.md) и [подписанного индекса](rooms-file-sync-index.md).

Последующий этап с пользовательским интерфейсом и наблюдением за сохранениями описан в [отчёте UI/watcher](rooms-file-sync-ui.md). Утверждения о ещё не подключённых UI и renderer IPC ниже относятся к состоянию сетевого этапа.

## Результат

`RoomManager` объединяет защищённый индекс, локальные привязки и существующий сетевой движок комнаты. Владелец создаёт общую папку и явно публикует сохранённую версию файла. Другой участник получает проверяемую историю; запись в его рабочую папку начинается только после отдельной локальной привязки с включённым автоприменением. Последующие версии сохраняют постоянный ID документа и резервные копии. Независимая локальная правка останавливает замену.

Это внутреннее подключение предварительной версии. По умолчанию оно выключено; локальный флаг `HAVVN_FILE_SYNC=1` включает сетевые обработчики. Нативный тест передаёт `new RoomManager({ fileSyncEnabled: true })`. Пользовательского интерфейса и renderer/preload IPC для управления синхронизацией пока нет. Установка флага сама по себе не выбирает папки и не запускает публикацию локальных файлов.

## Метаданные

`shared/room-file-sync-protocol.ts` задаёт capability `file-sync-v1`, подписанный конверт и сообщения предложения журнала, запроса страницы, страницы и подтверждения. Существующий `sync-v2` совместного просмотра не изменён.

Конверт связан с криптографическим контекстом комнаты, отправителем, адресатом, корнем и потоком. Подписи вложенных политик и ревизий проходят существующий входной фильтр движка до ретрансляции; основной процесс повторно проверяет семантику и полномочия через индекс. Участники без capability и гости не получают права отправлять команды синхронизации.

`RoomSyncExchange` передаёт причинный журнал страницами до 32 записей и 96 КиБ. Полная страница сначала проверяется и сохраняется одной записью защищённого индекса. Только после успешного сохранения передаётся ACK. Подтверждение относится к метаданным; оно не означает наличие содержимого у получателя. Потерянные подтверждения восстанавливаются повторным предложением журнала; повтор принятой страницы не добавляет версии.

Защитные ограничения: 8 корней на локальную комнату, 64 входящих/исходящих состояния обмена и 128 ожидающих сообщений. Сохраняются общие ограничения комнаты на байты, подписи, участников и идентичности. Новый корень регистрируется только после проверки исходной политики настоящего владельца. Сеть не переносит локальные пути, привязки и разрешение автоприменения.

## Содержимое

Запрос метаданных конкретной подписанной ревизии получает отдельный подписанный ответ. Дескриптор связывает info hash с именем, длиной и layout единственного файла. Проверка выполняется до `client.add()` и записи в download-каталог. После скачивания проверяются реальные куски, затем частная копия и E2E-расшифровка.

`RoomBlobTransport` использует WebTorrent-клиент самой комнаты, её трекеры, ограничения трафика, общую очередь получения и резервирование свободного места. Второго production-клиента WebTorrent нет. Версии синхронизации не добавляются в обычный `room.files`/манифест.

Снимки создаются с `private: true`: одинаковые обычная публикация и sync-снимок занимают разные info hash. Адаптер требует private torrent и удаляет из входных метаданных трекеры и web seeds, поскольку эти поля не защищены info hash и WebTorrent объединяет их с параметрами вызова. Обнаружение источников задаёт сама комната. В клиенте исправлено имя настройки отключения web seeds на фактическое `webSeeds: false`; LSD также явно выключен.

Подготовка локальной раздачи использует отдельную ограниченную очередь, чтобы встречные загрузки двух участников не заблокировали доступ к источникам. До 256 активных torrent-объектов принадлежат адаптеру; завершённые неиспользуемые раздачи вытесняются с сохранением файлов и подписанных ссылок. Запрос метаданных может повторно запустить раздачу сохранённой копии. Повреждённая собственная раздача заменяется только из проверенного источника; посторонний torrent с совпавшим hash не захватывается.

Служебные пути сокращены для Windows: локальный идентификатор каталога комнаты занимает 32 hex-символа, download получает эксклюзивный каталог `blob-*` без повторного длинного ID файла. Это устраняет обнаруженное в нативном тесте превышение ограничения `mkdtemp`.

## Жизненный цикл

`RoomSyncCatalog` хранит защищённый список корней. При перезапуске открывается и повторно проверяется индекс, согласуются файловые квитанции, проверяются сохранённые источники и восстанавливается ранее включённая привязка. Активация следует за принятым состоянием комнаты и не зависит от открытия панели или ещё одного HELLO. Повторное включение той же папки сохраняет отпечатки применённых версий; выбор другого пути их сбрасывает.

Остановка комнаты, выход, kick, сетевой suspend и закрытие менеджера отменяют обмен и передачу. Смена кода, владельца или E2E-контекста завершает старые задачи. Корни с несовпадающим контекстом показываются внутреннему API как приостановленные; автоматического переноса полномочий нет. Смена ключа внутри прежнего E2E-контекста позволяет восстановить старые версии при наличии ключа соответствующей эпохи.

Методы `listFileSyncRoots`, `createFileSyncRoot`, `bindFileSyncRoot` и `publishFileSyncFile` предназначены для доверенного основного процесса. Привязки не могут пересекаться с кешем, обычной папкой комнаты и другими активными корнями той же комнаты.

## Проверки

```powershell
npm run test:room-sync
npm run test:room-sync-network
npm run typecheck
npm test
npm run build
```

`test:room-sync-network` запускает два настоящих Electron-процесса с изолированными временными профилями, локальным WebSocket-трекером и Chromium WebRTC. Публичные трекеры и STUN в тесте отключены. Используются настоящие `RoomManager`, preload движка, подписи, защищённое Windows-хранилище и E2E. Успешный сценарий удаляет только собственные временные профили; при ошибке каталог сохраняется для диагностики.

Проверяются обнаружение корня без локальной привязки, отсутствие неявной записи, две последовательные зашифрованные версии, отсутствие sync-файлов в обычном манифесте, сохранение независимой правки при третьей версии и автоматическое восстановление привязки после перезапуска получателя. Нативный сценарий успешно прошёл на Windows; для DPAPI ему требуется запуск вне ограниченной песочницы.

Целевые тесты дополнительно проверяют потерю/перестановку ACK, отказ диска без подтверждения страницы, подделку исходной политики, ограничения очередей, повреждение содержимого, удаление внешних URL из torrent-метаданных, отмену и изоляцию посторонних раздач.

Результат проверки 17 октября: `test:room-sync` — 130 тестов в восьми наборах; полный `npm test` — 3222 теста Vitest и 8 проверок Node, без ошибок. Typecheck Electron/renderer/guest и сборки всех трёх частей прошли. ESLint новых модулей прошёл без замечаний; изменённые существующие модули проходят с предупреждениями текущего кода. Production-сборка renderer сообщает о размере bundle. Физические ПК, NAT/TURN и Office этим прогоном не проверяются.

## До выпуска

- Мастер выбора папки, предварительное сравнение, состояние, UI конфликтов и история с восстановлением.
- Наблюдение за сохранениями, повторные обходы, исключения, обработка rename-based save и постоянная очередь локальных изменений.
- Проверяемый переход корней после ротации кода/передачи владения; сейчас несовпадающие корни приостанавливаются.
- Квоты всей истории и кеша, компактация, освобождение неиспользуемых копий и очистка после leave/kick. Сейчас закрытие останавливает работу, но защищённая история и частные копии автоматически не удаляются.
- Общая проверка пересечения привязок между разными комнатами/процессами; сейчас проверяются активные корни внутри одного координатора комнаты.
- Проверки физических ПК, NAT/TURN, долговременного офлайна, смешанных установленных версий, Word/Excel/IDE и нагрузок на границе лимитов.
- Ограничения файлового прототипа сохраняются: hardlink, временное отсутствие рабочего пути между стадиями замены и отсутствие транзакции с произвольным внешним редактором. Подробности перечислены в первом отчёте.

Совместное редактирование с курсорами, двусторонние изменения, удаление и переименование пока не подключены. Текущий путь передаёт сохранённые версии как непрозрачные байты; он не объединяет содержимое DOCX/XLSX и проектов IDE.
