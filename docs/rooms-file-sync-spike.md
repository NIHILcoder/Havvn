# Синхронизация файлов: первый технический прототип

17 октября 2026 года. Связан с шагом 0 [плана реализации](rooms-file-sync-plan.md).

Это отчёт о первоначальном прототипе. Текущая интеграция с настоящими комнатами и Chromium WebRTC описана в [сетевом отчёте](rooms-file-sync-network.md); утверждения о ещё не подключённой сети ниже относятся к первоначальному этапу.

## Статус

Добавлен исполняемый изолированный прототип. Он проверяет работу с изменяемым исходником, передачу отдельных версий и восстановление пользовательского файла. Последующее развитие — подписанная модель, защищённый индекс и координатор — описано в [rooms-file-sync-index.md](rooms-file-sync-index.md). Включение синхронизации в интерфейсе, наблюдение за папками и сетевой API комнаты ещё не реализованы. Возможности клиентов не менялись.

## Принятые решения

1. Старый `RoomFile.fileId` остаётся идентификатором содержимого. Для прототипа существующий дескриптор используется только на границе проверки торрент-метаданных. Постоянный ID документа и подписанная история добавляются отдельно.
2. Для передачи создаётся частная копия исходника. Изменение оригинала внешним редактором не повреждает предыдущую раздачу. Подготовка сравнивает отпечаток исходника до/после копирования и проверяет полученные торрент-метаданные и байты.
3. В E2E-режиме используется существующее шифрование и `keyEpoch`. После подготовки в каталоге снимка остаётся шифротекст; локальный SHA-256 исходника не включается в `RoomFile` или торрент-метаданные.
4. Отдельный swarm WebTorrent может обслужить снимок без помещения версии в манифест комнаты. Это проверено на реальных клиентах с TCP-соединением через loopback. Для соединений комнаты ещё требуется адаптация контекста передачи и доступности.
5. При применении требуется ожидаемый хеш предыдущего файла либо явное отсутствие файла. Несовпадение останавливает замену. Новые байты проходят проверку в staging-каталоге до изменения назначения.
6. Журнал применения создаётся на том же томе, что и рабочий файл. Предыдущие байты сохраняются отдельно. Новая копия публикуется без перезаписи уже появившегося файла. При ошибке журнал остаётся для восстановления.
7. Используемый способ публикации требует hardlink. Возможность проверяется до перемещения оригинала; неподдерживаемый том отклоняется. Это ограничение прототипа, а не обещание поддержки любых дисков в выпуске.

## Код

- `electron/sharing/room-sync-snapshot.ts`: стабильные копии, ограничение размера 256 МиБ, потоковое хеширование, E2E и проверка метаданных существующими функциями.
- `electron/sharing/room-sync-apply.ts`: очередь на корень в пределах процесса, проверка относительных путей, staging, предыдущая копия, журнал, квитанция применения и консервативное восстановление.
- `electron/sharing/room-sync-files.test.ts`: сценарии локальной записи, конфликтов, Windows-блокировок, опасных путей и прерываний.
- `electron/sharing/room-sync-transfer.test.ts`: два реальных клиента WebTorrent, две версии одного файла, проверка байтов, применение, история; обычный и E2E-режимы.
- `scripts/spike-room-sync.cjs`: отдельный процесс принудительно завершается на контрольной стадии, новый процесс восстанавливает результат из файлов на диске.

## Восстановление

Контрольные стадии и ожидаемый результат:

- `prepared`: оригинал остаётся на месте; операция помечается отменённой.
- `previous-saved`: если рабочий путь свободен, предыдущая копия возвращается; подготовленные новые байты сохраняются.
- `published`: проверенные новые байты остаются рабочей версией; завершается квитанция применения.
- `committed`: квитанция читается без повторного изменения рабочего файла.

Если после прерывания в назначении появились независимые локальные данные, прототип возвращает `conflict` и сохраняет доступные копии. Повторная запись в такой корень блокируется до разрешения незавершённой операции. Терминальные операции допускают повторное чтение результатов; более поздняя локальная правка не отменяет уже завершённую транзакцию.

Возврат прежних байтов учитывает позднюю запись редактора в уже перемещённый оригинал. Повторный запуск обрабатывает и прерывание между созданием собственного hardlink и удалением второй ссылки. Подменённые и повреждённые записи журнала не применяются автоматически.

## Запуск проверок

Из корня репозитория:

```powershell
npm run test:room-sync
npm run spike:room-sync
```

Первая команда проверяет снимки, замену и реальную передачу через loopback. Публичные трекеры, DHT, LAN discovery, NAT mapping и PEX отключены. TCP-проверка не подтверждает работу через WebRTC, NAT или ретрансляторы комнаты.

Вторая собирает Electron-код и проверяет четыре завершения дочернего Node-процесса через `process.exit(73)`. Все файлы сценария находятся в эксклюзивном временном каталоге; пользовательские данные не используются. Это проверка завершения процесса, а не аппаратного отключения питания.

Дополнительно проверяются существующие `room-file-storage.test.ts` и `room-receive-integration.test.ts`, чтобы сохранить прежние гарантии проверки файлов и получения содержимого.

Результат проверки 17 октября: все 104 теста в четырёх указанных наборах прошли, включая реальный Windows-lock и обе loopback-передачи. `npm run spike:room-sync` успешно собрал Electron-код и проверил четыре стадии завершения отдельного процесса. ESLint новых TypeScript-файлов прошёл без ошибок. Полный набор тестов приложения и полная production-сборка renderer/guest на этом этапе не запускались: существующие runtime-пути ещё не изменялись.

## Что необходимо до подключения к пользователю

- Подписанные политика, ревизии, постоянные ID и защищённый индекс добавлены следующим этапом; см. связанный отчёт. Базовые файловые примитивы по-прежнему предназначены для доверенного координатора и не являются обработчиками удалённых команд.
- Адаптер к текущему движку комнаты, его управлению раздачами и жизненным циклом. Отдельные тестовые клиенты не заменяют проверку `room.files`/доступности/очередей внутри движка.
- Протокол пагинации, запросы недостающих версий, ограничения нагрузки и проверка смешанной сети старых/новых клиентов.
- Watcher, повторный обход и восстановление очереди исходящих изменений.
- Предварительное сравнение папки, UI конфликтов, явная привязка и согласие на локальное применение.
- Ограничение общего места, очистка staging и истории, reference counting. Сейчас история и осиротевшие копии намеренно не очищаются автоматически.
- Операции удаления/переименования, разрешение конфликтов и гранулярная блокировка отдельного файла вместо всего корня.
- Проверка параллельного доступа из разных процессов: имеющаяся очередь защищает только один процесс приложения.
- Реальная приёмка сохранений Word/Excel/IDE и редакторов с открытыми дескрипторами, допускающими удаление файла. Тест Windows проверяет `FileShare.Read`, запрещающий замену; он не моделирует все программы.
- Сократить окно между перемещением оригинала и публикацией новой версии. Исследовать `ReplaceFileW` с резервной копией либо иной проверенный механизм Windows. Пока при сбое путь может временно отсутствовать до `recover()`.
- Не заявлять транзакционность с произвольным внешним редактором: он может продолжить запись через открытый дескриптор после контрольной проверки. Журнал сохраняет копии, но не заменяет координацию с приложением.
- Проверка устойчивости при исчерпании диска, повреждении журнала и отказе файловой системы. `fsync` файлов не подтверждает долговечность всех переименований при отключении питания.
- Нагрузочные измерения 2000 файлов, файла на границе 256 МиБ и влияния на активный голос. Текущие сетевые проверки используют небольшие конфиги и не являются нагрузочным тестом.

Модель и локальный индекс добавлены следующим этапом. Далее — подключение blob-передачи и новых сообщений к существующему движку комнаты. Новую capability следует объявлять только после того, как соответствующие сетевые обработчики и проверки реализованы.
