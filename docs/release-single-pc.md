## Состояние кандидата

Текущий локальный снимок после [DP-03](device-pairing-data.md): 4290 Vitest-тестов, 30 Node-тестов, 123 целевых сценария и 28 нативных проверок main/renderer в трёх запусках Electron. Типы, линтер изменённого кода и сборка прошли. [Приёмка DP-03](device-pairing-data-acceptance.json) отдельно описывает renderer-кэш, first-run/keyring и предел 64 КиБ для snapshot. Linux-ноутбук доступен как оборудование, но подключение и физические прогоны ещё не выполнены.

После FUN-02/03/04 старые фазы FUN-01 `local`, `package`, `installer` имеют статус **stale**. Прочитано существующим сборщиком по текущим исходникам; исходные квитанции и старые доказательства не переписаны. Снимок чтения: `artifacts/fun06-release-current.json`. `releaseReady: false`.

Перед подготовкой FUN-06 общий Vitest выполнил **4167 успешных тестов в 319 наборах**, но завершился с двумя ошибками сбора: файлы `performance-heavy-metrics.test.cjs` и `room-release-acceptance.test.cjs` используют `node:test`, а не Vitest. Это конкретная найденная ошибка запуска проверок; её нельзя представлять как падение этих 4167 сценариев или как успешный общий прогон.

Исправлено разделение runners: пять известных Node-наборов исключены из Vitest и перечислены в `npm test`. Итоговый общий повтор завершил **4189 тестов в 320 наборах Vitest**, включая 22 проверки новой модели. Отдельный запуск всех пяти Node-наборов завершил **30 проверок**. Исходный неуспешный лог сохранён в `artifacts/fun06-baseline-vitest.log`, итоговый повтор — `artifacts/fun06-final-vitest.log`, Node — `artifacts/fun06-node-final.log`. Результаты модели сопряжения и итоговые хеши — [device-pairing-research.json](device-pairing-research.json).

## Что можно выполнить сейчас

1. Зафиксировать кандидат и незакоммиченные исходники существующим SHA-256 manifest. Отдельно сохранить результат типов, общего Vitest и Node-наборов. При ограничении нагрузки использовать `npx vitest run --maxWorkers=2`; Node-наборы запускаются отдельно той же пятёркой, что в `npm test`.
2. Перепроверить относящиеся к изменениям реальные сценарии: `npm run test:automation-ui`, `npm run test:engine-features-ui`, `npm run test:media-library-ui`, `npm run test:room-preflight-ui`. Они не заменяют сеть и пакет; прежние результаты остаются историческими для прежнего отпечатка.
3. Снять новую локальную фазу FUN-01 в отдельную директорию: `node scripts/room-release-acceptance.cjs run --phase local --output artifacts/release-candidate-20261026`. Она включает полноценные сценарии документов, редактора, нескольких авторов и ошибок записи, а не только общий набор unit-тестов.
4. После успешной локальной фазы выполнить `--phase package` с **тем же** `--output`, затем `--phase installer`. Используется существующий изолированный NSIS-план. Проверяются реальные renderer/preload/IPC, Native/Classic, worker, чистая установка, обновление тестового профиля и последующее удаление только тестовой установки. Публичная публикация, изменение основной установки, ассоциаций и пользовательского профиля не входят в этот запуск.
5. Повторить сравнительные performance-сценарии текущего кандидата: видимое/скрытое окно, тяжёлые разделы, видео с подготовкой файлов. Зафиксировать питание, эффекты, режим окна, длительность и настоящий GPU. Предыдущие цифры не превращать в измерения новой сборки.
6. Прочитать `report`/`gate` по этому же каталогу и сохранить ограничения. Без физического сетевого протокола gate должен оставаться незакрытым. Не редактировать вручную `passed-current` и не использовать две искусственные метки версии как настоящую старую сборку.

Эти фазы подготовлены к запуску; package/installer и реальные нагрузки **не выполнялись в рамках подготовки FUN-06**. Dev-процесс пользователя и его профиль не останавливаются. Проверка Electron с двумя локальными профилями по-прежнему означает один физический ПК.

## Что остаётся внешним

- FUN-01: подключение имеющегося Linux-ноутбука как второго физического ПК, реальные LAN/другая сеть/строгий NAT/пользовательский TURN, настоящая ранее выпущенная сборка и подписанный пользователем протокол. Оборудование доступно, доступ и прогоны ещё не настроены.
- FUN-06: после адаптеров/журнала DP-03 нужны UI/интеграция DP-04, затем проверка пары Windows ↔ Linux. Ни локальная модель, ни TLS/main/renderer на одном ПК не подтверждают физическую сеть.
- Приёмка другой ОС, реальной батареи и окружений, отсутствующих на этом ПК.

Шаблоны для будущей ручной приёмки: FUN-01 — `artifacts/fun06-physical-protocol.template.json`, FUN-06 — [device-pairing-physical.template.json](device-pairing-physical.template.json). Они не заполнены и не подтверждают успешных сценариев.

## Хранилища, которые нельзя смешивать при приёмке

- Main: `config.json` (настройки/категории/расписание/приватность), отдельные downloads/rss/search/blocklists/reputation и защищённые комнаты; их формат не равен переносимому JSON.
- PER-06: version 2 с выбранными разделами и отдельный `settings-transfer.json` для восстановления. Секреты и идентичность комнаты не переносятся.
- Renderer: разрешённые `INTERFACE_KEYS` и их схемы; отдельно история просмотра и предпочтения плеера. Наличие ключа в localStorage не разрешает отправлять его другому устройству.
- FUN-04: защищённый `automation.json` и квитанции вместе с загрузкой. Экспорт правил в PER-06 пока не реализован.
- FUN-06: DP-01 объединяет identity, пару и исходящую очередь в защищённом `devices/device-state.json` с marker привязки профиля. DP-02 проверил TLS и P-256 ключ с Ed25519 привязкой; DP-03 добавил причинные регистры и журнал применения в том же envelope. Инициализация явная, обычный профиль не менялся; UI/раннее восстановление — DP-04.
