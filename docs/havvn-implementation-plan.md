## 1. Как выполнять план

- Двигаться небольшими изменениями: модель и хранение → интеграция → интерфейс → проверка законченного сценария. Не объединять все направления в один PR.
- Для каждой задачи сохранять идентификатор из обзора: `UX`, `PER`, `OPT` или `FUN`. В описании изменения указывать закрываемые пункты и оставшиеся ограничения.
- Новые файлы в этом документе — предлагаемые места реализации. Перед созданием проверять существующие аналоги и следовать текущим соглашениям проекта.
- Отмечать задачу выполненной только после проверки критерия готовности. Статусы: «не начато», «в работе», «готово к проверке», «выполнено», «нужны внешние условия».
- Проверки проводить в изолированных профилях. Не использовать пользовательские загрузки и идентичность комнаты как тестовые данные.
- Сроки оценивать после этапа 0 и первого законченного изменения. `M` и `L` из обзора — относительная сложность, а не обещание календарных дат.

Первый пользовательский результат — исправленный перенос категорий. Первый законченный пакет удобства — перенос настроек, палитра команд, центр событий и сохранённые виды загрузок.

## 2. Зависимости и очередность

1. **Этап 0:** актуальное состояние и исходные замеры производительности.
2. **Этап 1:** перенос настроек и общая навигация с палитрой команд.
3. **Этап 2:** события, объяснимое ожидание, сохранённые виды и отмена удаления записи.
4. **Этап 3:** категории, уведомления, навигация и рабочие профили.
5. **Этап 4:** управление ресурсами, хранение и оптимизация подтверждённых узких мест.
6. **Этап 5:** приёмка синхронизации и документов, проверка совместимости.
7. **Этап 6:** медиатека, возможности движков и автоматизация.
8. **Этап 7:** исследование сопряжения собственных устройств.

Первичное знакомство и доступность выполняются по мере готовности новых экранов и завершаются перед выпуском соответствующего пакета. Этап 5 можно вести одновременно с этапами 1–4: для него уже есть реализация и отдельные проверки. Его результат не обязан задерживать выпуск независимых улучшений загрузок.

Ключевые зависимости:

- Палитра и избранное используют один реестр навигации и действий.
- Центр событий и уведомления используют один поток значимых событий.
- Сохранённые виды и политики уведомлений нужны до рабочих профилей.
- Контракт приоритетов настроек нужен до экономного режима и автоматизации.
- Исходные замеры нужны до утверждений об ускорении или снижении нагрузки.
- Сопряжение устройств начинается после стабилизации форматов переносимых настроек.

6. **Сохранённые виды загрузок:** условия, хранение, Sidebar, палитра и перенос.
7. **Отмена удаления записи:** снимок и восстановление обоих движков, затем UI.

Исходные performance-замеры фиксируются перед изменениями поведения; новые UI-сценарии добавляются в соответствующие проверки по мере появления. Количество PR в каждом пункте можно увеличить, если миграция или интеграция не помещается в одно обозримое изменение.

## 12. Проверки и выпуск

### Для отдельной задачи

- [ ] Проверки значимого поведения: миграция, конфликт, отказ записи, повторное действие, восстановление или вычисление приоритета — по характеру изменения.
- [ ] Typecheck и lint затронутого кода; UI-проверка реального компонента для нового пользовательского маршрута.
- [ ] Новые строки добавлены в `renderer/i18n/en.json` и `ru.json`; строки main-процесса — в его словарь.
- [ ] Обновлены документация и статус задачи. Прямые ссылки на существующие отчёты не подменяют повторную проверку изменённого поведения.

Не создавать отдельные тесты для простых текстовых правок и механического копирования реализации. Для миграций, записей на диск, протоколов, очередей и восстановлений проверять отказ и перезапуск.

### Перед выпуском пакета изменений

Существующие общие команды:

```powershell
npm run typecheck
npm run lint
npm test
npm run build
```

Связанные наборы запускать по затронутому поведению:

```powershell
npm run test:download-layout
npm run test:download-progress
npm run test:torrent-controls
npm run test:appearance
npm run test:startup
npm run test:room-sync
npm run test:room-documents
```

UI/E2E синхронизации, packaged и installer проверять по инструкциям соответствующих документов и скриптов: некоторые команды требуют отдельной сборки или пути к пакету. Новые команды, предложенные в ходе реализации, добавлять в `package.json` только вместе с работающими скриптами.

- [ ] Пройти обновление со старым профилем и запуск с чистым профилем.
- [ ] Проверить main, вынесенные окна и guest для затронутых возможностей.
- [ ] Для зависимых от движка изменений пройти Native и Classic; для платформенных — поддержку и корректный fallback.
- [ ] Сравнить согласованные performance-сценарии, если меняются частота обновлений, тяжёлые задачи или хранение.
- [ ] Сохранить результаты и ограничения; не переносить статус «проверено локально» на реальные NAT/двухмашинные сценарии.

### Совместимость и возврат

- Новые необязательные поля имеют безопасные значения по умолчанию; старый профиль продолжает открываться.
- Перед изменением формата сохраняется пригодная для восстановления копия; по возможности миграция добавляет новые данные, не уничтожая старые.
- Нельзя обещать downgrade только потому, что сохранена резервная копия: отдельно проверить, понимает ли предыдущая версия изменённые файлы.
- Отключение новой функции не удаляет её данные. Удаление истории, профилей или кешей — явное действие с подходящим предпросмотром.
- Существующие флаги экспериментальных функций сохраняются до закрытия их критериев выпуска; новые флаги вводятся только при реальной необходимости постепенной приёмки.
