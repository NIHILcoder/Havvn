Этот протокол фиксирует кандидата FUN-01 до последующих изменений
[FUN-05](room-preflight.md). После них отпечаток продукта отличается: контроль
выпуска помечает старые фазы как `stale`, пока соответствующие проверки нового
кандидата не будут выполнены. Сохранённые исходные результаты не переписываются.

Машиночитаемая сводка: `docs/rooms-release-acceptance.json`.
Исходные отчёты текущей приёмки и их хеши находятся в `artifacts/fun01/`.
Сводка содержит отдельные отпечатки исходников frontend/backend с общими типами
и относящихся к фазе скриптов проверки, завершённые команды, коды выхода,
версии runtime, SHA-256 журналов и отчётов.
Отдельно сохраняются хеши проверенных установщиков и `app.asar`.
Старые результаты выделены отдельно
и не превращаются в подтверждение новой сборки по одному успешному boolean.

## Объём и результат

Протокол разделяет три локальные фазы:

- `local` — текущие исходники, типы, тесты правил приёмки и протоколов,
  настоящие редакторы в изолированных Electron-профилях, права нескольких
  авторов, офлайн-возврат, смена владельца и восстановление после блокировки файла;
- `package` — новый неподписанный проверочный пакет, запуск настоящих
  renderer/preload/IPC и обоих движков, операция с торрентом, комната,
  редактирование документа и восстановление снимка упакованным CRDT-worker;
  дополнительно открывается настоящий редактор из `app.asar`, включая его
  отложенные JS-модули и новый индикатор сохранения;
- `installer` — новая установка и обновление через настоящие NSIS-скрипты,
  сохранность данных и выбора ярлыков, последующее удаление тестовой копии.

Состояния фазы: `passed-current`, `stale`, `not-run`, `failed` или
`evidence-invalid`. `passed-current` требует полного набора шагов текущей фазы,
совпадения снимка исходников и сохранённых хешей журналов и доказательств.
Для пакета дополнительно сверяются проверенный `app.asar` и фактический архив.
Прерванный прогон остаётся незавершённым.

В текущем прогоне прошли 173 модульных теста, включая девять состояний индикатора
сохранения, семь проверок самого сборщика протокола, проверка типов и сборка.
Настоящие Electron-сценарии документов завершили 18 проверок, сбои записи —
шесть; отдельно прошли файловый редактор и несколько авторов. Упакованное
приложение прошло оба движка, работу с документом и загрузку настоящего редактора.
Изолированный NSIS завершил девять проверок установки, обновления, сохранности
состояния и удаления. Установленный `app.asar` совпал с проверенным пакетом:
`67a15d2ebbc341553be16fddf6375008de3c604ecb0b9db0c7380acb12e31cae`.
Хеш основной установки и реальные обработчики `.torrent`/`magnet` не изменились.
Это результаты одного физического компьютера с изолированными профилями.

При первом сборе пакетного отчёта выявилось несовпадение формата: smoke-тест
успешно выполнил сценарии, но ещё не записывал хеш `app.asar`. После исправления
повторён именно этот тест на неизменённом архиве и проверки сборщика протокола.
Исходные журналы, первоначальный отказ и связь с повтором сохранены в
`reconciledFrom`. Отпечаток продукта отделён от скриптов проверки: исправление
формата отчёта не требует повторения неизменённых нативных сценариев.

Приёмка выполняется последовательно. Во время неё dev-сервер пользователя
не останавливается, обычный профиль и пользовательские комнаты не используются.
Сетевые тесты создают свои локальные трекеры и изолированные тестовые профили;
firewall, сетевые адаптеры, VPN и пользовательский TURN автоматически не меняются.

несколько авторов и сбой замены файла. Полный набор всех старых медиа-, LAN-
и серверных сценариев автоматически заново не запускается.

## Значение сохранения в интерфейсе

Редактор документов показывает разные состояния:

- несохранённый ввод остаётся в состоянии «Сохраняем…»;
- «Сохранено локально · ждём владельца» означает сохранённый на этом компьютере
  черновик, ещё не принятый в общую историю;
- «Общая версия подтверждена» означает принятие версии в общую историю.
  Получение каждым участником этой подписью не подтверждается; доступ зависит
  от прав и связи;
- восстановление, передача владельца и черновик, требующий проверки прав,
  имеют собственные состояния и не показываются как подтверждённая версия.

Проверка статуса учитывает также локальный черновик без ожидающих предложений.
Состояние только в памяти не выдаётся за устойчивую запись. Предупреждения,
проверка прав и сохранение отклонённого черновика остаются действующими.
Файловый редактор уже сообщает отдельно, что версия сохранена на этом устройстве
и поставлена на передачу участникам.

Ни индикатор, ни протокол не обещают восстановление данных, которых больше
нет ни у одного участника. При аварийном завершении отдельно учитываются
последняя подтверждённая локальная запись и ещё не сохранённый ввод.

## Изоляция установки

`prepare-installer-acceptance.cjs` создаёт отдельные имя приложения, appId,
реестровое пространство, ярлыки, файловые типы и URI-схемы. Перед запуском
план проверяется на принадлежность к `release/installer-acceptance/<id>`.
Основной Havvn не является целью установки или удаления. Стенд сверяет
его хеш и реальные `.torrent`/`magnet`-регистрации до и после проверки.

Оба тестовых установщика содержат один текущий код с метками 3.2.0 и 3.2.1.
Так проверяются замена NSIS и сохранение состояния; это не проверка двух
реальных исторических версий. Подпись издателя, онлайн-канал обновлений
и все исторические миграции этим прогоном не сертифицируются.

## Открытые внешние проверки

Для обычной LAN нужны два физических ПК и проверки изменения файлов,
конфликта, офлайн-возврата, настоящей Office-блокировки, совместных документов,
отзыва прав, недоступности владельца, передачи владения и перезапуска в ходе
записи. При перезапуске проверяется сохранность последней устойчивой версии;
потеря ещё не сохранённого ввода не маскируется успешным индикатором.

Для разных сетей, строгого NAT и пользовательского TURN отдельно проверяются
соединение, файл и документ. В протоколе фиксируются устройства, ОС, версия
приложения, хеш кандидата и доказательства фактического маршрута. Настройка
TURN без использования relay-кандидата не считается проверкой TURN.
Ретрансляция журнала через участника комнаты и TURN — разные маршруты.
Если строгий NAT не наблюдался, этот сценарий остаётся непроверенным.

Совместимость с настоящей ранее выпущенной версией также требует отдельного
прогона. Нужны разные исполняемые сборки с записанными хешами; смена метки
версии при одном коде не закрывает этот пункт. Локальные протокольные тесты
версий и прав фиксируются как локальные тесты, без подмены этого результата.

После появления второго ПК используйте [подготовку синтетических данных
и порядок ручного прогона](rooms-file-sync-acceptance.md#подготовка-ручного-прогона).
Каждое устройство создаёт свою идентичность и профиль: профили и ключи между
ПК не копируются. В протокол не включаются приглашения, ключи комнаты и
пароли TURN. Для реальной сетевой приёмки также применимы
[сценарии диагностики маршрутов](testing-rooms.md).

## Повторение и контроль выпуска

```powershell
npm run test:release-acceptance
npm run release:rooms -- run --phase local
npm run release:rooms -- run --phase package
npm run release:rooms -- run --phase installer
npm run release:rooms -- report
npm run release:rooms -- template

# После реальной внешней приёмки и ручной проверки протокола:
npm run release:rooms -- gate --external artifacts/fun01/physical-protocol.completed.json
```

`template` создаёт только новый файл и не перезаписывает заполненный протокол.
Шаблон содержит отдельные незавершённые сценарии; пустые поля не считаются
подтверждением проверки. Команда `gate` без внешнего протокола сохраняет выпуск
закрытым. Код выхода `2` означает незакрытую приёмку, `1` — ошибку данных или
выполнения, `0` — прохождение запрошенной команды; для `gate` ноль разрешён
только после выполнения всех его требований.

`gate` проверяет локальные доказательства и структуру явно рассмотренного
оператором внешнего протокола. Физическое расположение устройств и сетевые
наблюдения им самим не измеряются. Утверждение оператора остаётся ручной
частью приёмки. Без неё loopback, условные метки версий и промежуточный
участник не превращаются в подтверждение реальных устройств или TURN.

**Экспериментальный флаг `HAVVN_FILE_SYNC` остаётся на месте.** Сборщик протокола
ничего не включает и не меняет продуктовые возможности. FUN-01 целиком
не закрывается до оставшихся внешних проверок.
