# OPT-01 — экономный режим

Реализовано 25 октября 2026 года. Основание — [контракт эффективных настроек](effective-settings.md).

## Выбор и источник

В «Настройки → Система → Ресурсы и питание» доступны обычный, экономный и
автоматический режимы. По умолчанию выбран обычный: существующим установкам
экономия автоматически не включается. Выбор сохраняется в `AppSettings.resourceMode`
и переносится с настройками приложения. Живой источник питания не сохраняется
и не переносится между компьютерами.

Ручной обычный или экономный режим имеет приоритет над событиями питания.
В автоматическом режиме экономия действует только при подтверждённом питании
от батареи. При неизвестном питании показано отдельное состояние; действует
обычный режим, а экономию можно включить вручную.

На Windows и macOS используются `powerMonitor.isOnBatteryPower()`, события
`on-battery`/`on-ac`, повторная проверка после пробуждения и раз в 30 секунд.
Поведение API сверено с [документацией Electron](https://www.electronjs.org/docs/latest/api/power-monitor/).
На неподдерживаемой платформе или при ошибке запроса источник считается неизвестным.
Ручные режимы продолжают работать. Проверки сигналов батареи эмулированы; физическое
переключение батареи на тестовом настольном компьютере не выполнялось.

## Что ограничивается

- Для оформления применяется `light` и отключаются эффекты движения за указателем.
  Настройки темы, прозрачности, радиусов и локальные изображения не переписываются.
  Нативный материал окна остаётся под существующим управлением оформления/ОС.
- Обычные числовые показатели загрузок объединяются в последнее наблюдение
  и публикуются раз в секунду. При редком источнике (не чаще раза в секунду)
  дополнительного ожидания нет. Ошибка, пауза, завершение, смена стадии операции,
  причины ожидания и доступных действий публикуются сразу. Частота событий
  самого движка и сохранения статистики на диск не меняется.
- Автоматические миниатюры изображений в списке комнаты не запрашиваются.
  Явное открытие изображения двойным щелчком работает. Уже открытая картинка
  продолжает отображаться.
- Открытые сведения о файлах обновляются раз в пять секунд вместо одной.
  Первое чтение выполняется сразу; смена режима отменяет старый таймер.
- Фоновая предзагрузка следующей серии приостанавливается. В Classic очищаются
  только принадлежащие предзагрузке диапазоны, без текущего воспроизведения
  и пользовательского выбора файлов. Новые запросы проверяются также в host,
  включая повторный запуск host. На Native остаётся прежний статус отсутствия
  поддержки ограниченной предзагрузки; экономия не добавляет фиктивную поддержку.

Экономия не меняет скорости, лимит активных загрузок, VPN/дисковые блокировки,
сердцебиения сети, голос, запись данных, синхронизацию или текущий видеопоток.
Она не ограничивает CPU внешнего ffmpeg/игрового сервера; это отдельная задача OPT-04.

## Снятие ограничений и гонки

При возврате к обычному режиму оформление рассчитывается по текущим предпочтениям,
а не по снимку до включения экономии. Изменение темы во время экономии сохраняется.
Ожидающая числовая статистика публикуется сразу. Предзагрузка снова возможна только
при сохранённом разрешении пользователя и подходящем буфере/состоянии плеера;
её выключенное пользователем состояние не превращается во включённое.
Настройки предзагрузки можно редактировать и во время экономии: ограничение
блокирует фоновую работу, а не сохранение нового пользовательского выбора.

Состояние имеет монотонную ревизию. Запоздалое первоначальное чтение не может
перекрыть новое событие питания. Источник питания, пришедший во время чтения
настроек, также не заменяется старой выборкой. При потере IPC сохраняется последнее
полученное ограничение и выполняется повторное чтение. Подписка общая для окна;
размонтирование снимает подписки и таймеры. Отдельные UI-окна получают те же
атрибуты оформления через существующее зеркалирование popout.

Периодическое чтение списка загрузок не откатывает числовые показатели, ожидающие
публикации. Локальное удаление/изменение сначала согласует ожидающую статистику,
а затем применяет действие, чтобы таймер не воскресил удалённую строку.

## Проверки и воспроизведение

```powershell
npm run typecheck
npm run build:electron
npm run build:renderer
npx vitest run --maxWorkers=2
node --test scripts/dev-electron.test.cjs scripts/dev-renderer.test.cjs scripts/performance-baseline.test.cjs
node scripts/smoke-resource-mode.cjs
node scripts/measure-resource-mode.cjs
```

Целевые тесты покрывают матрицу режимов/источников питания, ручной приоритет,
неизвестное питание, событие во время чтения, ошибку сохранения и повторную попытку,
очистку наблюдателей, coalescing статистики, немедленные статусы, снятие ограничений,
гонку с DB-ответом и сохранение пользовательских диапазонов воспроизведения.
Выбор находится через поиск настроек на RU/EN.

UI-приёмка работает в изолированном временном профиле. Настоящий preload читает
состояние через IPC; контроллер использует настоящий store с эмулированным питанием.
Проверены ручной выбор, авто, неизвестный источник, правка оформления во время
экономии, восстановление предзагрузки и сведений о файлах, явное открытие изображения,
сохранение плеера и новый процесс Electron с ранее выбранным режимом.
Снимки RU/EN, тёмной/светлой темы, ширины 520 px и масштаба 125% находятся
в `artifacts/resource-mode-ui/` и просмотрены визуально. Это проверка UI и политик,
а не реальный звонок/просмотр фильма с измерением расхода аккумулятора.

## Методика сравнения производительности

Используется тот же UI-стенд OPT-02 с настоящими компонентами и production React
profiling. Три полных запуска обычного режима, затем три экономного; пять сценариев
в каждом, минимум шесть секунд записи на сценарий, 1500 мс прогрева. Входящие
синтетические показатели идут каждые 100 мс в обоих режимах. Исходники, bundle,
компьютер, питание, эффекты и данные должны совпасть; различаться может только режим.

Итог сохраняется в `artifacts/resource-mode-performance/comparison.json`, сырые
данные и трассы — в соседних `normal/` и `economy/`. Старый исходный эталон OPT-02
не перезаписывается. Его прежнее отсутствие полей режима/каденса интерпретируется
как обычный режим с обновлениями каждые 750 мс; экономный режим и другая частота
входящих данных не принимаются за одинаковые условия сравнения бюджетов.

Основная целевая метрика — работа React при частой числовой статистике. CPU и
память относятся ко всем процессам изолированного стенда Electron, без настоящих
torrent/room/voice backend. Окно скрыто, оформление минимальное, уменьшение движения
включено; эта серия не измеряет аппаратную экономию GPU, стоимость реального
стекла или расход батареи. Новые значения счётчиков могут отображаться позже
по замыслу режима, поэтому время доставки счётчика нельзя выдавать за улучшение
задержки команды или отрисованного кадра.

Порядок запусков последовательный, а не случайный; фоновая работа компьютера
сохраняется. Диапазоны повторов нужно учитывать при оценке CPU и памяти.

## Итоговая проверка реализации

Полная регрессия после правки частоты обновлений: **4049 тестов в 307 файлах**,
без ошибок (`artifacts/resource-mode-vitest-final.json`). Node-часть — **17 из 17**,
включая совместимость прежнего performance-эталона и запрет сравнения разных
режимов/частот как одинаковых условий. TypeScript Electron/renderer/guest прошёл;
сборки Electron и renderer успешны. Webpack оставил три предупреждения о размере
и организации bundle; ошибок сборки нет. ESLint новых модулей и планировщика
статистики прошёл без ошибок.

UI-прогон завершил **22 содержательных сценария**, не считая повторных открытий
селекта и служебных отметок завершения. После последней правки проверено также
редактирование разрешения предзагрузки во время экономии: новый отказ сохраняется
и не отменяется при возврате в обычный режим. Новый процесс Electron прочитал
сохранённый ручной экономный режим при неизвестном питании.

Ранние замеры до исправления планировщика статистики сохранены отдельно в
`artifacts/resource-mode-performance-preflight-delayed-counters/` и не входят
в итоговое сравнение. Проверка неизменности исходников отклонила эту раннюю серию.

## Итоговое сравнение 25 октября 2026

Три повтора каждого режима завершились успешно: 30 сценариев и 30 сжатых трасс.
Время серии: 16:45:22–16:50:08 МСК. Исходники: `0e7daf0beff6…`, bundle:
`7aa3d7e85d2f…`; полные хеши — в `comparison.json` и manifest. CPU: Ryzen 5 3600,
питание от сети. Проверка после серии подтвердила неизменность исходников.
Проверены одинаковые исходники, bundle, условия и наборы данных. Перед окончательной
серией завершены полная регрессия и сборка; параллельно с замерами тесты не запускались.

На 100 и 1000 синтетических загрузок число commits React составило **62 → 10**
в каждом из трёх повторов: уменьшение на **83,87%**. Это число подтверждённых
обновлений React в записи, а не кадров монитора. В каждом сценарии поданы
60 пакетов статистики с номинальной паузой 100 мс после обработки пакета.
Фактическая длительность записи немного больше шести секунд и сохранена в raw JSON.

Для 1000 загрузок медиана среднего CPU всех процессов тестового Electron-стенда
составила **0,735% → 0,625%**: около **15,0%** относительно исходного значения,
или **0,111 процентного пункта**. Диапазоны трёх повторов: обычный — 0,678–0,771%,
экономный — 0,612–0,627%. На 100 загрузках: 0,636% → 0,562%.

В истории комнаты число commits осталось 121, в повторных открытиях — 138
в обоих режимах. Уверенное улучшение этих сценариев не заявляется: их обновления
не отключались экономным режимом, а диапазоны CPU пересекаются. Пустой сценарий
не имел commits; ему не приписывается процент уменьшения перерисовок.

Измеренный результат относится к частой синтетической статистике, минимальному
оформлению и profiling-сборке на этом компьютере. Он подтверждает снижение
работы UI в целевом сценарии; его нельзя переносить на расход батареи, GPU,
производительность настоящих передач или обычный источник с редкими пакетами.
При пакетах раз в секунду или реже экономия не добавляет ожидание; остальные
ограничения оформления, миниатюр, сведений о файлах и предзагрузки продолжают действовать.
