# OPT-02 — воспроизводимая исходная серия интерфейса

Стенд расширяет существующие `performance-renderer.cjs` и общий profiling entry,
не меняя поведение продукта. Пять сценариев запускаются в отдельных окнах,
а каждый повтор серии — в новом процессе Electron и отдельном временном профиле:

- пустые загрузки и отсутствие комнат;
- 100 активных загрузок;
- 1000 активных загрузок;
- комната с 1000 файлами, 10 000 сообщениями и 2000 записями истории;
- восемь циклов открытия комнаты и возвращения к 1000 загрузкам.

Используются настоящие App, страницы, строки и CSS. Backend, torrent/room engines,
голос и игровые процессы не запускаются, внешняя сеть блокируется. Файлы и
сообщения — данные фикстуры; байты файлов по сети не передаются.

## Воспроизведение

```powershell
npm run performance:ci
npm run performance:baseline -- --runs 3 --gpu --output artifacts/performance-baseline/current
npm run performance:baseline -- --runs 1 --gpu --compare artifacts/performance-baseline/current/summary.json --output artifacts/performance-baseline/candidate
node --test scripts/performance-baseline.test.cjs
```

Короткий режим проверяет структуру и освобождение подписок; он не калибрует
численные пороги. Полный режим: три повтора, 1500 мс прогрева и минимум 6000 мс
записи на сценарий. Stats/room updates подаются через 750 мс, поэтому фактическая
длительность может быть чуть больше. Пятисекундный опрос загрузок попадает в запись.
Сценарий повторных открытий содержит восемь циклов и дополняется ожиданием до
минимальной длительности. GC не форсируется.

Первое окно использует свежий профиль; последующие — прогретый runtime/профиль
этого процесса. Кеш ОС не очищается. `startupMs` — время от загрузки окна до
готовности начальной страницы загрузок, а не полный production-старт с daemon.
Время готовности процесса Electron хранится отдельно как `electronReadyMs`.

Задержка действия включает управление через `executeJavaScript`, ожидание нужного
DOM и два оборота очереди событий. Физический показ кадра не ожидается: скрытое
окно может ограничивать `requestAnimationFrame`. Для комнаты в задержки также
входит её первое открытие перед записью обновлений. Эти измерения нельзя выдавать
за задержку реального клика до пикселя на мониторе.

## Метрики и происхождение

- CPU по PID/роли — исходное значение API Electron за интервал между запросами.
  Первый/слишком короткий интервал и отрицательное значение помечаются как
  недостоверные. В JSON сохраняются raw-значения и длительность интервала;
  неизвестное не заменяется нулём. Сводка использует среднее допустимых выборок.
  Определение интервала сверено с [CPUUsage Electron](https://www.electronjs.org/docs/latest/api/structures/cpu-usage).
- Private bytes и working set всех процессов **стенда Electron**, а также V8 heap
  интерфейса записываются отдельно. Parent Node, наблюдатель PowerShell и реальные
  production backend-процессы сюда не входят. Память main включает расходы стенда;
  результат не является полным потреблением работающего Havvn с передачами.
  Единицы исходного MemoryInfo — килобайты согласно [документации Electron](https://www.electronjs.org/docs/latest/api/structures/memory-info); в сводке они переведены в МиБ.
- React commits/вызовы компонентов, задержки таймеров renderer/main, число узлов
  DOM, API-вызовы и подписки. Счётчики показывают работу настоящего UI.
  В новых сводках отдельно сохранены число commits и суммарное число вызовов
  инструментированных компонентов.
- Объём синтетической границы — UTF-8 размер JSON запросов, ответов и push-событий.
  Сериализация добавляет наблюдательную нагрузку. Это не размер настоящего Electron
  IPC и не сетевой трафик; содержимое пользовательских данных не собирается.
- CDP-трассы сохраняются в gzip: Paint, DrawFrame, Layout и прочие события. Сумма
  вложенных длительностей не является эксклюзивным временем. У скрытого окна
  compositor может не рисовать кадры; ноль событий не означает нулевой GPU.
- `--gpu` отдельно читает Windows GPU Engine только для PID стенда. CPU роли GPU
  и аппаратные счётчики не смешиваются. Если соответствующих строк нет, аппаратная
  утилизация считается неопределённой, а не нулевой. Чужие PID/процессы не сохраняются.
- Сохраняется занятость CPU всего компьютера за сцену, включая фоновую нагрузку.
  Dev-сервер пользователя не останавливается. Числа являются локальной исходной
  серией в этих условиях, а не обещанием производительности на другом компьютере.

`source-manifest.json` содержит HEAD, список изменённых/новых файлов и SHA-256
исходников, конфигурации, package-lock и скриптов. Хешируется также построенный
bundle. Изменение исходников во время сборки/серии прерывает приёмку.
Условия включают ОС, CPU/RAM, Electron/Chromium/Node, GPU/драйвер/доступные функции,
питание, схему питания, размеры данных, эффекты, масштаб окна, прогрев и длительность.

## Пороги и CI

После трёх полных повторов для каждой доступной метрики вычисляется предварительный
порог: максимум значений повторов плюс наибольшее из 40% максимума, тройного разброса
и фиксированного запаса для данной метрики. Формула и пороги сохраняются в summary.
Для задержек сначала считается p95 каждого запуска, затем медиана трёх p95;
для памяти — медиана каждого запуска, затем медиана этих медиан. p95 использует
nearest rank. Рядом сохраняются все значения повторов и их диапазон.

Сравнение разрешено только при одинаковых условиях и данных. Новая версия исходников
допускается; смена компьютера, ОС, драйвера, питания, режима, длительности или данных
требует новой калибровки. Нельзя перезаписать эталон папкой результата сравнения.
Превышение порога завершает команду с ошибкой, сохраняет список превышений, сырые
данные и трассы. Неполный запуск не превращается в успешную сводку.

Windows CI запускает короткий прогон: одна подписка статистики, ограниченное число
строк DOM, размонтирование тяжёлого экрана и отсутствие накопления подписок после
переходов. Аппаратные/численные пороги другого компьютера в CI не применяются.
Данные остаются локально в рабочем каталоге runner; внешняя выгрузка не подключена.

Для OPT-01 добавлены `--resource-mode normal|economy` и `--stats-tick-ms`.
По умолчанию это обычный режим и прежние 750 мс. Парное сравнение выполняет
`node scripts/measure-resource-mode.cjs`; [условия и ограничения](resource-mode.md).
Старые эталоны без этих двух полей сохраняют исходную семантику normal/750 мс.

## Артефакты и границы приёмки

В `artifacts/performance-baseline/current/` находятся `run-1…3.json`, `summary.json`,
manifest и сжатые трассы. Диагностические пробные прогоны хранятся отдельно;
`preflight-3s` не входит в итоговую серию. При ошибке сохраняются `failure.json`,
состояние сценария и при UI-тайм-ауте — диагностический снимок.

На основе итоговой серии создаётся интерактивный Canvas с выбором метрик, диапазоном
повторов и предварительными порогами. Исходные JSON остаются источником чисел.

Настоящие совместные нагрузки описаны отдельно: [рецепты](performance-load-recipes.md).
Их результаты в эту синтетическую серию не входят. Существующий видимый стенд
`performance-idle-renderer.cjs --verify-idle` предназначен для отдельной проверки
непрерывной перерисовки; скрытая серия его не заменяет.

32.0.16.1664. Три процесса × пять сценариев, минимум шесть секунд на сценарий.
Эталон относится к исходникам `675c2732d274…` и bundle `cb1eb0fa702b…`;
полные хеши и состояние Git находятся в manifest и JSON.

Задержки команды до готового DOM, медиана трёх p95: 100 загрузок — 7,56 мс;
1000 — 8,70 мс; история комнаты, включая первое открытие — 215,01 мс;
повторные открытия комнаты — 181,80 мс. У пустого сценария действий нет,
поэтому ему не приписана нулевая задержка. Это исходная серия без утверждения
об ускорении. Полные диапазоны, CPU, память и пороги доступны в summary и Canvas.

Аппаратный счётчик Windows доступен, но записей engines для тестовых PID
в скрытом окне не вернул. Аппаратная утилизация в этой серии не определена.
CPU GPU-процесса сохранён отдельно и не подставляется вместо неё.

Проверка предельного случая выполнена отдельным запуском `overrun-check`:
в копии эталона намеренно установлен порог startup 0 мс. Команда завершилась
с кодом 1, сохранила пять превышений, пять трасс и `failure.json`.
Этот запуск не входит в исходную серию. Итоговый короткий CI-прогон также прошёл;
16 Node-проверок включают восемь новых проверок статистики и полноты результатов.
Canvas проверен TypeScript по установленному SDK. ESLint изменённых скриптов
прошёл без ошибок. Автоматическая выгрузка артефактов в GitHub отклонена проверкой
разрешений и не включена; диагностика остаётся локальной.

Общая регрессия: итоговый полный прогон с двумя воркерами — 3995 тестов
в 298 файлах, без ошибок (`vitest-repeat.json`). Предыдущий прогон с четырьмя
воркерами дал два сбоя в `room-srv-cmd.test.ts`: первая команда не была доставлена,
и следующий тест не получил кадр для повторной отправки. Этот файл отдельно
прошёл 7 из 7 тестов; в полном повторе сбой также не воспроизвёлся. Причина
не установлена; код комнаты и её тесты в OPT-02 не менялись. Оба отчёта сохранены
рядом с диагностикой стенда. Отдельные 16 Node-проверок прошли без ошибок.
