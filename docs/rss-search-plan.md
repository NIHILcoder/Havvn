# RSS и Поиск — план апгрейда

Status: **все фазы сделаны** (2026-08-18).

Цель: довести два раздела, которые сейчас работают «на минималках», до уровня,
ради которого их вообще держат в торрент-клиенте — RSS как **движок правил**
(качает нужное само и без дублей), Поиск как **инструмент выбора** (а не список,
из которого жмут первую строку сверху).

## Срез «как сейчас»

| RSS | 1 фид = 1 include-regex = 1 путь | правил, эпизодов, exclude/размера/сидов, категорий, паузы |
| Поиск | агрегат по провайдерам, сортировка по сидам на бэкенде | дедупа, сортировки в UI, действий на строке, отмены, видимости провайдеров |

## Фаза 0 — баги (самодостаточно, API не ломает) — **СДЕЛАНО**

Делать первой: без неё часть фидов и все нелатинские заголовки просто не работают.

Итог: сеть вынесена в `electron/utils/http-fetch.ts` (пункты 1, 3, 4), разбор
фида — в `shared/feed-parse.ts` (пункт 2), остальное правлено на месте. Тесты:
`shared/feed-parse.test.ts` (21), `electron/utils/http-fetch.test.ts` (9).

1. **Кодировка.** Чтение потока без `setEncoding('utf8')` —
   `rss-service.ts:152`, `search-service.ts:370`. Многобайтовый символ на границе
   чанка → `�`. Копить буферы, склеивать в конце, декодировать один раз
   (с учётом charset из `Content-Type`).
2. **Atom.** `parseRSS` знает только `<item>` (`rss-service.ts:170`) — фиды с
   `<entry>` добавляются, выглядят живыми и всегда пусты. Добавить ветку
   `<entry>` + `<link rel="alternate" href>` + `<updated>`; попутно
   `<media:content>`, `nyaa:infoHash`, `torrent:seeds`.
3. **Редиректы.** `rss-service.ts:142` и `search-service.ts:362` идут по
   `Location` рекурсивно: нет счётчика прыжков (цикл крутится вечно), нет
   резолва относительно базы (относительный `Location` падает с «Invalid URL»).
   Лимит 5 прыжков + `new URL(location, base)` + запрет схем кроме `http(s)`.
4. **Потолок размера тела.** Ни в одном из двух fetch нет лимита — фид или ответ
   на сотни МБ буферизуется в память. Обрубать на ~10 МБ с внятной ошибкой.
5. **Догоняющая проверка.** `initialize()` (`rss-service.ts:21`) только вешает
   `setInterval`. Фид с интервалом 6 ч после рестарта молчит ещё 6 ч, хотя
   `lastChecked` вчерашний. Считать «просрочен ли» по `lastChecked` и прогонять
   сразу; интервалам добавить джиттер ±10%, иначе все фиды с дефолтными 30 мин
   стучат одной пачкой.
6. **Батч-запись.** `autoDownload` зовёт `markRSSItemDownloaded` в цикле
   (`rss-service.ts:287`) — каждый вызов переписывает весь массив (до 5000
   элементов) на диск. Один `markRSSItemsDownloaded(guids[])`.
7. **Torznab-парсер строже, чем нужно.** `/<item>/` без `[^>]*`
   (`search-service.ts:150`) не переживает `<item ...>`; регулярка `torznab:attr`
   требует строгий порядок `name`→`value` в двойных кавычках. Ослабить обе.

**Приёмка:** фид Nyaa (Atom) отдаёт элементы; заголовок с кириллицей приходит
целым; фид, отдающий 302 на относительный путь, читается; рестарт приложения с
просроченным фидом даёт проверку в первые секунды.

## Фаза 2 — Поиск — **СДЕЛАНО**

Итог: `search:query` заменён на `search.start` → события `search:progress` →
`search.cancel`; дедуп в `shared/search-dedupe.ts` (19 тестов), парсер caps в
`shared/torznab-caps.ts` (11 тестов), таблица в `SearchPage.tsx` перестроена на
виртуализацию с сортировкой, фильтрами, полосой провайдеров и меню на строке.
Сохранённые поиски (часть 2.8) осознанно отложены в фазу 3 — это правило без
URL ленты, и писать движок дважды смысла нет.

### 2.1 Дедупликация (главное)

Схлопывать по `infoHash`; при его отсутствии — нечётко по нормализованному
заголовку (нижний регистр, выкинуть разделители и теги качества) + размеру ±1%.
В строке — бейдж «N индексеров», сиды берём максимальные, ссылки копим все.

### 2.2 Прогрессивная выдача и отмена

Сейчас `Promise.allSettled` (`search-service.ts:41`) ждёт самого медленного, а у
script-провайдера потолок 25 с. Перевести на push: IPC-событие `search:partial`
с `{ searchId, provider, results }`, финал — `search:done`. Добавить
`search:cancel(searchId)` и лимит параллелизма (сейчас 20 script-провайдеров =
20 одновременных python-процессов).

### 2.3 Видимость провайдеров

Падение уходит только в лог (`search-service.ts:51`) — юзер видит «ничего не
найдено» без причины. Возвращать и рисовать:

```ts
interface ProviderStat {
  name: string;
  count: number;
  ms: number;
  error?: string;
  state: 'pending' | 'ok' | 'failed';
}
```

### 2.4 Таблица результатов

`SearchPage.tsx:285` — ни одной кликабельной колонки. Добавить: сортировку
(имя / размер / сиды / дата), порог сидов, «скрыть мёртвые», чипы провайдеров и
категорий, уточнение по тексту, виртуализацию (`@tanstack/react-virtual` уже в
зависимостях).

### 2.5 Действия на строке

Сейчас одна кнопка «Скачать» в путь по умолчанию. Добавить: копировать magnet,
открыть страницу релиза, **превью файлов до добавления** (`getTorrentInfo` уже
есть — `types.ts:998`), выбрать путь и категорию, добавить на паузе.

### 2.6 Метаданные, которые уже приходят и выбрасываются

- Jackett: `r.Tracker` игнорируется, в колонке провайдера у всех строк одно и то
  же имя (`search-service.ts:120`) — показывать реальный индексер.
- Torznab: парсятся 5 атрибутов из десятков; взять `grabs`,
  `downloadvolumefactor` (freeleech), `imdbid`.
- Из заголовка — чипы 2160p / HEVC / релиз-группа, возраст релиза.

### 2.7 Категории от индексера (`t=caps`)

Список категорий захардкожен newznab-номерами (`SearchPage.tsx:24`) и для
`custom` / `script` не значит ничего. Тянуть `t=caps` у torznab-провайдера,
кешировать, строить выпадашку под выбранных провайдеров. Туда же `testProvider`:
пусть дёргает caps, а не шлёт настоящий поиск по слову «test».

### 2.8 Кэш, история, сохранённые поиски

LRU по `(query, category, providerSet)`, TTL ~5 мин + явное «обновить»; история
запросов; **сохранённый поиск с автозагрузкой** — по сути RSS без URL фида,
ложится на тот же движок правил из фазы 3.

**Приёмка:** поиск по популярному запросу с 3 индексерами даёт один ряд на
торрент; первые результаты видны раньше, чем ответил самый медленный; упавший
провайдер виден в шапке; выдачу можно отсортировать по размеру и добавить строку
в категорию.

## Фаза 3 — RSS — **СДЕЛАНО**

Итог: `shared/release-parse.ts` (31 тест) и `shared/rss-rules.ts` (29 тестов) —
разбор релизов и матчинг правил, чистые и общие для сервиса, превью и тестов.
`RSSRule` в сторе с миграцией `filter` → правило. Здоровье ленты, бэкофф и
условный GET — в `rss-service.ts`. Вкладка «Правила» с живым превью — в
`RSSPage.tsx`. Поля `filter` и `autoDownload` убраны из формы ленты (правила
их заменили), но остались в типе ради миграции.

### 3.1 Правила автозагрузки (главное)

Сейчас автозагрузка прибита к фиду — один фид = одна regex = один путь
(`types.ts:912`). Нельзя «качать сериал из любого фида», нельзя два правила на
один фид, нельзя выключить правило не трогая фид.

```ts
export interface RSSRule {
  id: string;
  name: string;
  enabled: boolean;
  feedIds: string[];          // [] = все фиды
  mode: 'wildcard' | 'regex'; // wildcard по умолчанию — regex пишут единицы
  include: string;
  exclude?: string;
  minSize?: number;
  maxSize?: number;
  minSeeds?: number;
  maxAgeDays?: number;
  savePath?: string;
  categoryId?: string;        // из фазы 1
  addPaused?: boolean;        // из фазы 1
  smartEpisode?: boolean;     // 3.2
  startFrom?: string;         // "S02E03"
  lastMatch?: string;
}
```

### 3.2 Умный фильтр эпизодов

Понятия «эпизод» нет вообще — фид с четырьмя релиз-группами приносит четыре копии
одной серии. Нужен парсер `S01E05` / `1x05` / абсолютной нумерации + резолюция,
кодек, группа; дедуп по `(шоу, сезон, эпизод)` в пределах правила; порог
«начиная с S02E03»; пропуск уже имеющегося. Парсер — в `shared/`, без
Electron-импортов, с юнит-тестами рядом (как `shared/search-parse.test.ts`).

### 3.3 Превью и ручной прогон

Правило невозможно отладить вслепую: показывать в редакторе, **что оно матчит на
уже накопленных элементах**, и давать разовое «дозабрать пропущенное».

### 3.4 Здоровье фида

Хранить `lastError`, `lastStatus`, `consecutiveFailures`, `lastItemCount`;
экспоненциальный бэкофф на падающих; красная точка вместо серо-зелёной
(`RSSPage.tsx:265`). Сейчас 404 и здоровый фид выглядят одинаково.

### 3.5 Условный GET

`ETag` / `Last-Modified` на фид, обработка 304, `Accept-Encoding: gzip`. Трафик
падает почти до нуля, трекеры с рейт-лимитами перестают ругаться.

### 3.6 Хранилище элементов

`merged.slice(-5000)` глобально (`store.ts:1540`) — один шумный фид вытесняет
историю тихого. Лимит на фид + ретенция по возрасту (30 дней). Плюс состояние
элемента шире, чем `downloaded`: `read` / `ignored`.

**Приёмка:** правило «Show X, 1080p, не HDTV, из всех фидов, в категорию
Сериалы» качает по одной серии на эпизод; фид с 404 подсвечен и опрашивается
реже; повторная проверка неизменившегося фида не качает XML.

## Порядок и зависимости

```
Фаза 0 (баги) ──┬─> Фаза 2 (Поиск)
                └─> Фаза 3 (RSS)

Фаза 1 (categoryId / paused) ──> нужна и в 2.5, и в 3.1

Фаза 3.1 (правила) ──> 2.8 (сохранённый поиск = правило без фида)

Фаза 4 — в любой момент после своей фазы
```

Рекомендуемая последовательность релизов: **0 → 1 → 2 → 3 → 4**. Фаза 0 не ломает
ничего и её можно выпустить патчем. Фазы 1–3 меняют типы и хранилище — нужна
миграция стора: `filter` фида превращается в авто-созданное `RSSRule`, чтобы
существующие подписки не потеряли поведение.

## Вне скоупа (осознанно)

- Свой встроенный индексер или хардкод трекеров — приложение принципиально не
  знает адресов, всё через Jackett / Torznab / плагины.
- Полнотекстовый поиск по уже скачанному — отдельная тема, не про этот раздел.
- Возврат `archive`-провайдера — archive.org отключил публичную выдачу .torrent
  (см. комментарий в `search-service.ts:84`).
