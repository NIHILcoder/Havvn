# DP-02. Защищённый loopback-прототип

26 октября 2026 года. Стадия проверяет транспорт между двумя независимыми профилями на одном ПК. FUN-06 остаётся открытым: адаптеров настроек, журнала применения, IPC и пользовательского маршрута пока нет. Обычный запуск Havvn не создаёт listener и не включает сопряжение.

## Реализация

- `electron/devices/bootstrap.ts`: одноразовое приглашение и два обязательных callback согласия, без значения по умолчанию «разрешено».
- `electron/devices/transport.ts`: TLS-сервер и клиент, жёстко ограниченные `127.0.0.1`. LAN-адрес из приглашения отклоняется до подключения.
- `electron/devices/wire.ts`: ограниченные кадры с длиной, строгий UTF-8, JSON, таймауты и безопасные ошибки.
- `electron/devices/session.ts`: повторное взаимно аутентифицированное соединение, восстановление prepared/active и повторная проверка текущего grant перед отправкой и выдачей входящего сообщения.
- `electron/devices/vault.ts`: TLS-фабрики без запуска listener, доступ только к публичной записи партнёра и уведомление транспорта при отзыве/ошибке хранения/закрытии.

## Почему формат идентичности стал v2

Настоящий Electron выявил то, чего не показал Node/OpenSSL: сертификат Ed25519 из DP-01 отклоняется в TLS с `ERR_SSL_NO_COMMON_SIGNATURE_ALGORITHMS`. Затем прямая передача самоподписанного P-256 leaf как trust anchor дала `UNABLE_TO_VERIFY_LEAF_SIGNATURE`; этот лог сохранён в `artifacts/dp02-native-leaf-failure.log`. Обход проверки сертификата не используется.

Новая публичная идентичность имеет вложенную версию **2**. Версии приглашения, кадров и защищённого контейнера остаются 1:

- Ed25519 остаётся ключом идентичности, её SHA-256 deviceId и подписей подтверждения пары.
- Отдельный P-256 ключ используется только для TLS leaf-сертификата с CA=false, SAN имени устройства, digitalSignature и EKU serverAuth/clientAuth.
- Для каждой идентичности выпускается отдельный P-256 CA с pathLen=0, который подписывает этот leaf. CA private key не экспортируется и не сохраняется; JS/WebCrypto не обещает гарантированного стирания памяти.
- Ed25519 `certificateProof` подписывает канонический домен `havvn/device-tls-certificate/v2`, deviceId, SPKI идентичности, хеши leaf и CA. Замена любого из них не проходит проверку.
- Оба сохраняемых приватных ключа находятся в одном OS-защищённом payload. CA не устанавливается в системное хранилище доверия: его получает только отдельный TLS context для конкретного партнёра.

Нативная проверка проверяет подпись цепочки, срок, SAN, назначение, тип/кривую TLS-ключа и подпись привязки. TLS дополнительно проверяет цепочку доверия и точное совпадение закреплённого leaf/SPKI. `rejectUnauthorized` включён; стандартная проверка имени не подменяется безусловным успехом.

Старая экспериментальная v1 запись читается без перезаписи ключей, однако TLS-фабрика отвечает ошибкой `version`. Тихого обновления идентичности/действующей пары нет. Миграция старого исследовательского профиля и продление сертификатов остаются отдельной работой до выпуска; пользовательские профили в этой стадии не создавались и не мигрировались. Свидетельство DP-01 описывает прежний формат и сохранено как историческое.

Основание для различия runtime: [Electron использует BoringSSL](https://www.electronjs.org/docs/latest/tutorial/using-native-node-modules). Конкретная несовместимость алгоритма и leaf-доверия выше — результат наших нативных проверок, а не утверждение обо всех версиях Electron.

## Первый обмен и восстановление

1. B проверяет приглашение, идентичность A, срок и области. Callback B должен явно вернуть `true` до сетевого подключения.
2. B подключается к закреплённому A через TLS 1.3. В bootstrap A ещё не знает сертификат B и не принимает его за доверенный TLS client certificate.
3. B передаёт свой публичный пакет, token и challengeB внутри проверенного канала. A строит challengeA и тело с обеими идентичностями, leaf-хешами, grant, точными областями и реальным TLS exporter. B сверяет каждое поле с приглашением и своим соединением.
4. B сохраняет pending и подписывает тело своим Ed25519 ключом. A проверяет подпись, токен и точное совпадение с телом текущего соединения, затем получает отдельное согласие A. Только после этого появляется подпись A.
5. После обеих сохранённых подписей стороны обмениваются подписанными prepared receipts и фиксируют active. Bootstrap-соединение закрывается; операции по нему не передаются.

Используется `EXPORTER-Channel-Binding`, 32 байта, пустой context по [RFC 9266](https://www.rfc-editor.org/rfc/rfc9266.html). Синтетического channel binding в транспортной проверке нет. Прозрачный TCP relay сохраняет сквозной TLS; подмена TLS-идентичности отклоняется pinning, а перенос подписанного подтверждения между двумя завершёнными TLS-соединениями отклоняется по exporter/challenge.

Потеря финального ответа может оставить A active и B prepared. Оба уже сохранили обе подписи, поэтому новое mTLS-соединение к закреплённому партнёру может идемпотентно обменяться прежними prepared receipts и завершить тот же grant. Отдельный session frame сверяет новый live exporter и grant. Это восстановление коммита, а не новый bootstrap со старым токеном. В состоянии pending без обеих подписей такой путь запрещён: требуется отменить попытку и создать новый grant.

## Сессии, права и границы ACK

Последующие соединения требуют client certificate, сертификат сервера и точный pin обоих партнёров. Разрешены только TLS 1.3 и ALPN `havvn-device-v1`. Сессии не кешируются приложением, resume callback не возвращает сохранённое состояние, включён `SSL_OP_NO_TICKET`; `isSessionReused()` отклоняется дополнительно на обеих сторонах. Обработка кадров начинается после secure handshake.

В Node 24.18.1 тест фактически получает TLS 1.3 tickets, повторно предлагает исходный opaque session state до/после отзыва и подтверждает новый handshake. Там же Git OpenSSL 3.5.7 проверил Max Early Data=0. Для диагностического парсера снята только [оболочка имени хоста Node 24.18.1](https://github.com/nodejs/node/blob/v24.18.1/lib/internal/tls/wrap.js); для настоящего replay используется исходный буфер. Декодированное содержимое сессионных секретов не выводится и не сохраняется. Дополнительный вызов Git OpenSSL выполняется только если эта утилита есть; проверка replay от неё не зависит.

В проверенном Electron 44.4.2 выдача tickets полностью подавлена: native.json явно содержит tickets=0 и maxEarlyData=null. Это не выдаётся за повтор реального нативного ticket. Ранние данные не разрешены; проверены отсутствие dispatch до TLS handshake, нулевой лимит в Node и запрет возобновления. Отдельный генератор корректных 0-RTT записей не запускался.

`DeviceSession.send` сверяет текущий grant, область и наличие операции в устойчивой outbox непосредственно перед `socket.write`, без await между проверкой и записью. `receive` повторяет проверку после ожидания кадра; неверные участники, ACK или схема закрывают соединение. Полученный authenticated ACK фиксируется через vault, но входящая операция **не вызывает автоматический ACK** и не меняет настройки. В DP-03 ACK можно будет отправлять только после устойчивого журнала применения.

Отзыв синхронно приостанавливает доступ и закрывает подписанные на vault открытые соединения ещё до записи tombstone. Ошибка записи сохраняет paused-error и запрет отправки; успех сообщается после чтения записанного состояния. Новый grant не оживляет старые сообщения. Уже отправленные до отзыва байты нельзя отозвать обратно; DP-03 обязан повторять проверку непосредственно перед применением уже полученной операции.

## Ограничения ресурсов

Кадр ограничен 64 КиБ, очередь — четырьмя кадрами, буфер — четырьмя максимальными кадрами с заголовками; больше четырёх ожидающих сообщений закрывают соединение. Разрешена одна незавершённая запись и одно ожидающее чтение. Сервер ограничен восемью TCP-соединениями и одной текущей bootstrap-попыткой. Handshake имеет таймаут 5 секунд, простой канала — 15 секунд. Эти параметры исследовательские: ожидание реального пользовательского решения и отмена UI будут спроектированы в DP-04.

Стандартные JSON/inspect представления канала и сессии не включают payload или ключи. Ошибки и callback диагностики возвращают ограниченные коды. Закрытие канала освобождает подписку сессии на vault.

## Проверки

Команды:

```powershell
npm run test:device-tls
npm run test:device-tls-native
npm run typecheck
npm run build
```

Целевой набор: **81 тест в 6 файлах**, включая 23 транспортных сценария. Проверяются согласия, неверный token/key/certificate, срок и версия, подмена scopes/fingerprint/exporter, перенос подтверждения между каналами, mTLS без сертификата/с другим ключом, потерянный финальный ответ, повтор старого token, отзыв/ошибка записи/новый grant, неверный ACK, фрагментация, переполнение, UTF-8, ALPN и TLS 1.2.

Полный регрессионный прогон: **4248 тестов Vitest в 325 файлах** и **30 Node-тестов**, без ошибок. Проверка типов всех трёх сборок и линтер изменённого кода прошли. Полная сборка прошла с тремя прежними предупреждениями webpack о размере/структуре bundle; установщик в этой стадии не проверялся.

Нативный стенд `scripts/smoke-device-tls.cjs`: **17 проверок, 6 процессов Electron, 2 изолированных профиля и 1 физический ПК**. Две пары процессов работают одновременно; затем оба профиля дважды открываются новыми процессами. Используются настоящий safeStorage/DPAPI и реальный TCP/TLS. Команды стенда зашифрованы в временных файлах, результаты/приглашения идут по приватным stdout pipes и не печатаются в логи. После завершения удаляется только проверенный временный каталог. Callback согласия детерминированный тестовый, реального UI-согласия этот стенд не подтверждает.

Общий результат, хеши исходников/логов и точные версии runtime: [приёмка DP-02](device-pairing-transport-acceptance.json). Поле OpenSSL `0.0.0`, которое публикует Electron, сохраняется как есть и не считается версией OpenSSL. Нативный TLS работает через BoringSSL.
