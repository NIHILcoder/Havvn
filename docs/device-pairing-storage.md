# DP-01. Идентичность и защищённое состояние устройства

Реализовано 26 октября 2026 года. Это backend для следующего прототипа FUN-06: сетевого listener, IPC, кнопки и автоматического запуска пока нет. В обычном профиле Havvn новые ключи не создаются до явного вызова backend.

## Идентичность и сертификаты

Каждый профиль создаёт собственный Ed25519 key pair через Node WebCrypto. `deviceId` — SHA-256 DER SPKI публичного ключа. Ключи комнат и восстановление `rooms.json` не используются. Приватный ключ не попадает в публичный снимок состояния или перенос настроек.

Для выпуска X.509 выбран `@peculiar/x509` **2.2.0**, для его Reflect API — `reflect-metadata` **0.2.2**; обе прямые зависимости закреплены в `package.json`/lockfile. Используется штатная реализация WebCrypto, без собственного ASN.1-кодировщика. [API библиотеки](https://github.com/PeculiarVentures/x509) использован для создания leaf-сертификата: Ed25519, `CA=false`, digitalSignature, serverAuth/clientAuth, SAN из полного deviceId, срок один год и запас пять минут перед началом действия.

Node/OpenSSL независимо проверяет подпись сертификата, тип ключа, совпадение SPKI/deviceId, SAN, срок, EKU и соответствие приватного ключа публичному. Нативная проверка создания TLS context также пройдена. Это проверка использования библиотеки и формата, а не внешний криптографический аудит или приёмка TLS handshake. Истёкший/повреждённый сертификат не вызывает скрытого выпуска новой идентичности; продление потребует отдельного решения перед выпуском.

## Единая запись

Вместо трёх независимых файлов из первоначального проекта используется одна атомарно заменяемая запись:

- `devices/device-state.json`: version 1 с одним OS-protected payload. Внутри — identity, revision, приглашение с хешем токена, текущая пара и её доказательства, tombstones отозванных grant, счётчики, ACK и outbox.
- `devices/device-state.marker`: публичная отметка инициализации и привязка каталога. Приватных ключей или токена в ней нет.

Весь полезный payload проходит через существующие строгие `encryptSecret/decryptSecretStrict`. При недоступной защите ОС, повреждённом ciphertext или Linux `basic_text` нет подстановки base64/plaintext. Перенос настроек PER-06 эти файлы не экспортирует.

На Windows проверен настоящий DPAPI. Он не защищает от другого приложения с теми же правами пользователя или компрометации самого ПК — это [граница safeStorage в Electron 44.4.2](https://github.com/electron/electron/blob/v44.4.2/docs/api/safe-storage.md). Стандартные JSON-сериализация и Node inspect экземпляра vault возвращают только публичный статус. PEM находится в памяти main при открытом vault; закрытие убирает ссылку, но гарантированное стирание всех копий JS-строки не обещается.

Привязка включает канонический каталог, платформу и filesystem device/inode. Обычное копирование в другой каталог отклоняется до замены identity. Отсутствие ciphertext при сохранившемся marker считается повреждением, а не новым профилем. Ошибки чтения и неизвестные версии сохраняют исходные данные. Нельзя использовать копию каталога для сопряжения второго ПК.

Это не аппаратная защита от полного клона VM, отката всей файловой системы или восстановления старого vault в том же каталоге с прежними ключами ОС. Такой перенос/откат не поддерживается. Внутри процесса проверка ожидаемого ciphertext замечает внешнюю замену файла и останавливает запись; после полного отката вне приложения отдельного аппаратного монотонного счётчика нет.

## Один владелец и запись после сбоя

Backend runtime доступен только main-процессу с существующим `app.hasSingleInstanceLock()`. Он ограничивает каталог собственным `userData`, включая проверку ближайшего существующего родителя, и не позволяет обходить владение через произвольный внешний путь. Внутри процесса второй handle одного vault отклоняется. Низкоуровневый файловый адаптер сам по себе не является межпроцессной базой данных: он используется с этим условием одного владельца.

Изменения сериализуются. Перед записью проверяются схема, квоты, подписи и ожидаемое старое содержимое. Новый зашифрованный файл пишется во временный файл, `fsync` завершается до атомарной публикации. Первая публикация не перезаписывает чужой файл. Временные файлы после неудачной публикации очищаются. На Windows проверена устойчивость к аварийному завершению процесса после коммита; отключение питания и полное поведение накопителя не тестировались.

Счётчик операции и сама outbox-запись находятся в одном payload. Операция возвращается вызывающему коду только после публикации и чтения результата. При неопределённой ошибке после записи экземпляр блокирует новые действия; повторное открытие читает реально сохранённую версию. Нельзя продолжать выдавать номера из устаревшего состояния памяти. Начальный marker намеренно не удаляется при неполной инициализации: требуется разбор, а не незаметная замена ключей.

## Схемы, подтверждения и grant

`shared/device-pairing.ts` определяет версии приглашения, тела согласованного grant, подписанных подтверждений, prepared receipt, операции и ACK. Неизвестные поля/версии, посторонние участники контекста, слишком большой/deep JSON, опасные имена ключей, неверные счётчики и некорректные адреса отклоняются. Лимит wire frame — 64 КиБ; outbox — 1000 операций и 8 МиБ. Значение операции пока ограниченный JSON: реальные allowlist-адаптеры предпочтений/видов/просмотра относятся к DP-03 и не подменяются этой схемой.

Одноразовый токен приглашения возвращается только создавшему его backend-вызову. На диске сохраняется его SHA-256, проверка использует `timingSafeEqual`. Погашение ограничено сроком приглашения и закрепляется за одним партнёром/транскриптом. Точный повтор шага допустим; другой ключ, изменённый challenge, отменённое приглашение или неверная подпись не подходят.

Канонические подписи отделены по доменам `confirmation/v1` и `prepared/v1`. Они связывают роли, обе идентичности, оба fingerprint сертификатов, invite/pair/grant, области, challenges и channel binding. Подпись другого участника проверяется его закреплённым ключом. Вызов локального подтверждения требуется на обеих сторонах; в этой стадии это backend-метод, а не уже готовый диалог согласия.

Состояния — `pending`, `prepared`, `active`, `revoked`. Для `prepared/active` при каждом открытии обязательны обе корректные подписи. `active` требует также проверенного prepared receipt партнёра. Потерянный ответ повторяется идемпотентно. Получение самого grantId не даёт прав. ACL на области можно только сузить; расширение требует нового подтверждённого grant.

## Отзыв

Запрос отзыва сразу блокирует отправку в текущем экземпляре, затем сохраняет tombstone grant и очищает его очередь. Последняя проверка выбранного сообщения запрещает отправку после отзыва или выключения области. Успех возвращается после устойчивой записи; повтор не создаёт второй tombstone и не пишет файл заново.

При отказе записи экземпляр остаётся `paused-error`; исходный файл сохраняется, доступен повтор отзыва с перечитыванием фактического состояния. Если ОС совсем не записала отзыв и процесс затем потерян, устойчивого подтверждённого отзыва нет — обратного обещания нет. Успешный отзыв проверен после нового процесса. Старые ready receipts, операции и ACK не подходят к новому grant. История отозванных grant не стирается по таймеру; при достижении 256 записей новые действия требуют отдельного решения, а не выбрасывания tombstones.

Существующий сертификат устройства не становится «удалённым» при отзыве одной пары. Будущий транспорт DP-02 обязан проверять текущий grant/ACL после TLS и непосредственно перед dispatch: принятие TLS context не равно разрешению синхронизации.

## Проверки

`npm run test:device-vault` — 56 тестов в 5 файлах, включая 22 прежние проверки исследовательской модели. Новые проверки покрывают сертификаты и подписи, схемы/канонизацию, состояния/повторы, отсутствие обоих подтверждений, очереди/ACK, отмену/срок приглашения, потерю ключа, неизвестную версию, ошибку защиты ОС, ошибки до/после записи, потерю файла, копию профиля и повтор старого grant.

`npm run test:device-vault-native` — настоящий runtime/preconditions, Windows DPAPI, два независимых identity-каталога внутри временного Electron-профиля и четыре процесса. Проверяются отсутствие открытого ключа/токена, копия профиля, аварийный выход после коммита до ACK, восстановление очереди, отказ атомарной публикации, запрет уже выбранного пакета, повтор отзыва и ещё один перезапуск. В сценарии **синтетический channel binding**, нет TLS-сокета, соединения между ПК или пользовательского подтверждения в UI.

Общий прогон: **4223 Vitest-теста в 324 наборах**, отдельно **30 Node-тестов**. Нативный сценарий содержит **25 проверок в четырёх процессах**. Типы, production-сборка и линтер новых файлов прошли; webpack сохранил три предупреждения о размере сборки. Общий исторический lint проекта этим не объявляется чистым. Логи сохраняются в `artifacts/dp01-*.log`. Нативный отчёт — `artifacts/dp01/native.json`; итоговые хеши и точный объём — [device-pairing-storage-acceptance.json](device-pairing-storage-acceptance.json). Предыдущие доказательства FUN-06/FUN-04 не переписываются и относятся к своим снимкам.

DP-01 не снимает экспериментальные флаги комнат и не закрывает FUN-06. Следующая стадия — DP-02: настоящие TLS-соединения между изолированными процессами, привязка к живому exporter, проверка сертификатов/ключей, MITM/повторы и отзыв с открытой сессией. Физическая приёмка на двух ПК — DP-05.
