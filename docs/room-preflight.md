# FUN-05. Проверка возможностей перед совместным действием

Обновлено 26 октября 2026 года. Проверено локально на Windows.

Общая проверка возвращает `status`, `reason`, `next` и `canAttempt`:

- `supported` — известные условия выполнены;
- `unsupported` — нужная возможность явно отсутствует или нет локального драйвера/API;
- `unknown` — нет объявления возможности либо ещё нет наблюдения соединения;
- `unavailable` — временное ограничение: участник отключился, движок не готов,
  защита остановила сеть, владелец не определён, права изменились или LAN занята.

У неизвестной возможности `canAttempt: false`. У ещё не измеренного соединения
`canAttempt: true`: пользователь может начать попытку. Отсутствие измерения
не выдаётся за строгий NAT, неисправность TURN или брандмауэра. Ограничение
показывает причину и следующий шаг. Успешные условия не добавляют галочку
или отдельный баннер.

## Где применяется

**Браузерный гость.** До входа видны ограничения документов, синхронизации папок,
зашифрованных файлов, LAN и управления комнатой. Наличие Web Crypto и WebRTC
проверяется при показе входа и повторно по нажатию; без API вход отключён.
Проверка не создаёт peer connection и не запрашивает микрофон. Поддержка
конкретного криптографического алгоритма, медиакодека и рабочий маршрут
выясняются при операции, а не объявляются измеренными.

**Совместный просмотр.** Панель объясняет ограничения. Включение синхронизации
запрашивает свежую проверку через preload/main и сверяет ведущего после ожидания.
Если ведущий отключился или перестал объявлять `watch-v2`/`watch-host-v1`,
совместный режим не включается; локальный просмотр сохраняется. Назначить
ведущего может текущий владелец: main повторно проверяет полномочия и поддержку
участника перед отправкой команды. Подписанный протокол движка продолжает
самостоятельно проверять полномочия.

**LAN.** Старт и принятие приглашения учитывают драйвер, защиту, занятость LAN,
актуальное приглашение и возможности участника. В выборе игроков клиенты без
объявления `lan` отключены с причиной. Устаревший выбор блокирует подтверждение,
но его можно убрать. Состав проверяется повторно после существующего
подтверждения и в main до запуска helper, после его ожидания и перед командой
движку. Если условия изменились, полученный helper останавливается.
Индикатор выбора — точка из CSS по центру, без символа галочки.

**Синхронизация.** В библиотеке показывается общий результат проверки.
Каждый вход в файловый сервис заново проверяет локальную возможность и состояние
комнаты, включая выбор папки и подтверждение. Права на конкретный корень,
редактирование и актуальность подтверждения проверяет сам сервис. Проверка
совместимости не предоставляет права записи. Локальные черновики документов
и их отдельная проверка прав сохраняются.

## Контракт и совместимость

Реализация: `shared/room-preflight.ts`. Main использует возможности собственной
сборки и действующий экспериментальный флаг. Удалённые объявления служат только
проверке совместимости и не предоставляют полномочий.

`rooms.preflight(roomId, action, targetId?)` — только чтение: без создания
движка, входа в комнату, сетевого теста, изменения адаптера или запроса разрешений.
IPC принимает известные действия и проверяет формат идентификаторов. Ответ
содержит фиксированные коды и boolean, без приглашений, ключей, адресов и имён.

Новых сетевых capability не потребовалось. Корректные приветствия будущего
протокола сохраняют известные возможности; неизвестные строки игнорируются.
Отсутствие объявления у старого клиента не считается поддержкой новой операции.
Обычный совместный режим без назначенного ведущего сохраняет прежнюю
совместимость; выбор клиента для нового режима требует явного объявления.

Канал комнаты означает наличие управляющей связи, а не доставку файла,
декодирование видео или качество media/LAN-маршрута. LAN считается наблюдаемой
при активной сессии и подключённом удалённом участнике. Маршрут и качество
по-прежнему описывает [диагностика соединения](rooms-connection-diagnostics.md).

## Проверки

Прошли 224 теста в семи файлах: неизвестные и отсутствующие возможности,
будущая версия, потеря поддержки назначенного ведущего, отзыв полномочий,
изменение состава до отправки команды и остановка нового helper при изменении
условий во время его ожидания.

Нативная UI-проверка завершила девять сценариев: локализованные состояния,
отсутствие баннера успеха, отключённый старый клиент, выбор без галочки, изменение
состава во время подтверждения, размещение при 1100/700/400 px и вход гостя
с доступными API, без WebRTC и без Web Crypto. Используются настоящие React,
Electron и собранный guest.js; состав синтетический, сеть блокируется.
Снимки и отчёт: `artifacts/fun05/ui/`.

Отдельно прошёл настоящий Electron-сценарий нескольких авторов синхронизации:
подписанные права, зашифрованные конкурирующие ветки, явное объединение,
перезапуск и отзыв прав. Профили изолированы; LAN-адаптер не создаётся.
Проверены типы main/renderer/guest и production-сборка. ESLint завершился без
ошибок; предупреждения крупных файлов сохранены в журнале. Сводка с хешами:
`docs/room-preflight-acceptance.json`.

```powershell
npm run test:room-preflight
npm run typecheck
npm run build
node scripts/smoke-room-preflight.cjs

# Нативная синхронизация с изолированными профилями:
node node_modules/webpack-cli/bin/cli.js --config scripts/room-sync-ui.webpack.cjs
node scripts/smoke-room-file-sync.cjs --ui --writers
```

FUN-05 не сертифицирует физическую LAN, строгий NAT или пользовательский TURN.
Внешние условия [FUN-01](rooms-release-acceptance.md) остаются незакрытыми.
Его прежний протокол относится к предыдущему кандидату; изменения FUN-05 меняют
отпечаток продукта, поэтому контроль выпуска помечает старые фазы как `stale`.
Перед выпуском нового кандидата соответствующие фазы повторяются.
Экспериментальный флаг `HAVVN_FILE_SYNC` не снимается.
